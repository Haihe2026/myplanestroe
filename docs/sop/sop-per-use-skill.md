# 频次类 Skill 开发 SOP

本 SOP 适用于**频次类付费 Skill**：按使用次数或有效结果计费（例如一次搜索、一家公司线索、一位联系人），通常需要调用外部数据接口，用**人民币余额**扣费，付费走 myplanestore.com。

- 生图类、扣 token 的技能 → 用「通用生图类 Skill 开发 SOP」。
- 全免费的技能 → 不适用本 SOP，按负责人开发时的说明临时调整。
- 拿不准属于哪一类 → 先问负责人，不要自行判断。

**执行要求：严格按阶段顺序推进。每个阶段的产出齐了才进入下一阶段。遇到「⛔ 决策关口」必须停下，等负责人明确确认后才能继续。不得跳过阶段，不得自行放宽固定规则。**

参考案例：外贸获客 `mps-linkedin-buyer-radar` 2.0.0（2026-10-25 上架）。

## 〇、开工前必读：WorkBuddy 官方开发文档（强制）

**所有 WorkBuddy 开发工作开工前，必须先读取 WorkBuddy 官方开发文档**，包括新开发、重构、优化、修 bug、改文案、打包上架。

1. **必读入口**：https://open.workbuddy.cn/docs/expert （专家），并按要做的产品类型读对应页面：
   - 技能：https://open.workbuddy.cn/docs/skill
   - 专家团：https://open.workbuddy.cn/docs/expert-team
   - 连接器：https://open.workbuddy.cn/docs/connector
   - 开放平台操作指引：https://open.workbuddy.cn/docs/what-is-open-platform
2. **每次开工都重新读线上最新版**，不凭记忆、不只读本 SOP 里的摘要。读完在工作记录里写一行：「已读 WorkBuddy 官方文档（日期、读了哪几页）」。
3. **官方文档优先**：本 SOP 与官方文档冲突时，以官方文档为准，先停下报负责人，确认后再改本 SOP。
4. 读不到文档（网络受限、页面改版）时，停下告诉负责人，不得按记忆继续开发。
5. 官方文档没写清的问题（例如字段长度、审核标准），不推定，发邮件问 openworkbuddy@tencent.com 或在开放平台社群里问，答复记进踩坑记录。

**官方要点摘要（2026-11-04 阅读；只作索引，以线上文档为准）**

- **技能包**：目录为 `SKILL.md`（必须）+ `references/`、`scripts/`、`templates/`（可选）；正文里用 `@references/xxx.md` 引用参考资料。frontmatter 必填：`name`、`display_name`、`display_name_en`、`description`（用途和触发词）、`description_zh`（详情页中文简介）、`description_en`、`version`、`author`（合作方名称）；可选 `allowed-tools`（工具白名单）、`examples_zh` / `examples_en`（详情页「试试这样用」）。
- **专家包**：目录为 `.codebuddy-plugin/plugin.json`、`avatars/`、`agents/<name>.md`、`README.md`。`plugin.json` 必填 `name`、`expertType`（agent / team）、`version`（语义化版本）、英文 `description`、`author`（name、email）、`agents`、`agentName`；展示字段全部必填：`displayName`、`profession`、`displayDescription`（中英，**中文 40–50 字**）、`avatar`、`categoryId`（15 个行业分类之一）、`plugin`（与 name 一致）、`defaultInitPrompt`（**必须和 quickPrompts 第一条一致**）、`tags`（**正好 3 个**）、`quickPrompts`（**正好 3 个**）。专家团另需 `teamInfo`（leadAgent、memberAgents）。
- **Agent 定义文件**（`agents/*.md`）：frontmatter 必填 `name`、`description`、`displayName`、`profession`，可选 `maxTurns`（默认 50）、`skills`；正文就是系统提示词。**开发者不能自己加工具**，工具由系统分配。
- **依赖**：MCP 和连接器在 `plugin.json` 的 `dependencies` 里声明（或根目录 `.mcp.json`），认证方式为 oauth / token / none；token 用表单和 `${VAR}` 占位，**禁止在包里硬编码真实 token 或 Key**。
- **头像**：PNG（优先）或 JPG，512×512 像素，不超过 500KB，放在 `avatars/`。
- 提交 zip 后解析失败时，先对照官方目录结构和字段说明排查；官方提供专家模板 `design-experts.zip`。
- 入驻流程：注册入驻 → 资质认证 → 创建业务类型 → 完善信息和能力配置 → 提交审核 → 发布上线 → 运营和版本维护。

## 一、固定规则（不得修改）

1. **欢迎句固定**：「欢迎使用WorkBuddy官方认证技能 <技能名>。」只替换末尾技能名，其余一字不改。
2. **付费只走 myplanestore.com**，不使用 AISkill 或任何其他平台的计费。
   - 通用付费页：`https://myplanestore.com/pay?skill=<后端技能标识>`，按 skill 参数显示本技能的标题和档位，不得出现其他技能的标题、配图或文案；
   - 通用档位：¥29 / ¥49 / ¥99。
3. **钱包**：频次类技能用该技能独立的**人民币钱包**，充值 1:1 入账（¥29 → 2900 分），不发 token，也不动 token 钱包。
4. **免费试用默认没有**。目前的例外：外贸获客每天免费搜索 1 次。新增例外必须经负责人确认。
5. **账号关联用方案 A**：网站记住浏览器登录态，WorkBuddy 新对话通过设备关联链接回原账号。不得在对话里索要手机号、验证码、密码或支付信息。
6. **技能标识**：新技能统一使用 `mps-` 前缀，后面用**有含义的英文**，不用拼音（例：`mps-gift-advisor`，不用 `mps-songli`）。更换标识等于新的上架条目，旧条目的下载量不会继承，用户已做的技能收藏（记忆锚定）也会失效；改名前先告知负责人。
7. **如实声明**：数据来源、覆盖范围、拿不到什么，写进 SKILL.md 和上架文案；不得宣称官方合作或认证。
8. **不收费的情况必须写明并实现**：零结果、档案缺失、上游失败、字段映射失败、额度保护触发时，一律不扣用户费用。
9. **单价做成后台可配置**，SKILL.md 和话术里不写死金额，通过 `status` 命令读取实时单价告诉用户。
10. **面向用户的文字里，严禁出现开发过程的内容（原则性错误）**。面向用户的文字包括：上架名称、一句话简介、详细描述、触发词、标签、使用示例、英文简介、SKILL.md 的 description、README，以及 SKILL.md 里让 AI 对用户说的话术。这些文字只写用户需要知道的：能做什么、怎么用、怎么收费、有什么局限。严禁出现：
   - 负责人和 AI 的对话内容，以及「按你说的」「已确认」「已改为」「G2 通过」这类开发过程用语；
   - 修改原因和版本对比，例如「相比旧版」「修复了……」「新版改为……」「旧版转化只有 6%」；
   - 内部信息：SOP 阶段和关口、踩坑记录、成本、毛利、供应商额度、后端接口、字段名和错误码；
   - 写给 AI 的执行指令（例如「不要编造」「先调用 status」「必须征得确认」）。这些只能写在 SKILL.md 正文的执行说明里，不得写进 description 和上架文案。

   **唯一例外**：description 末尾、触发词之后，允许一句固定格式的「调用倾向句」（见第五章），这是让宿主不 @ 也能选中技能的必要写法，不算违反本条。除这一句外，description 里不得出现其他给 AI 的指令。

   写完后逐句检查：一个第一次看到这个技能的用户读到这句话，是否需要、是否看得懂。不是，就删掉。
11. **不推定生产行为**：服务端支持什么（查询参数、范围、等待时长等），以服务端实际确认为准。没确认的能力不写进对用户的承诺，交给 Codex 确认后再放开。
12. **用户数据统计（遥测）只做「首次对话上报」一项，且必须做**。其他任何统计默认不做，要做必须负责人确认，并在 SKILL.md 和上架文案里明示收集什么。首次对话上报的统一做法：
    - 走服务端既有协议 `POST /platform-api/telemetry/v1/first-dialogue`，由脚本在第一轮完成，**每个安装只发一次**（本地写标记），有界 2 秒、不重试、失败即弃，不阻塞也不拖慢第一轮，不靠宿主调用；
    - 只报 9 个字段：`event_id`、`installation_id`、`machine_id`、`skill_id`、`skill_name`、`skill_version`、`channel`、`client_occurred_at`、`is_test`（`machine_id` 须等服务端白名单加上后才发，见第六章）；**不含用户原话、提示词、图片、账户或手机号**；服务端字段白名单严格，多一个键整条返回 400；
    - 两个标识都在本机随机生成：`installation_id` 每个技能每次安装一份；`machine_id` 每台机器一份，**只在我们自家技能之间共用**，不从硬件、MAC 地址、序列号等推导，不是设备指纹；服务端按「安装标识 × 技能 × 渠道」去重。完整口径见第六章；
    - 账户关联后调用 `/first-dialogue/link` 接到账户上（幂等），用于计算「首次对话 → 开通 → 付费」转化；
    - 提供关闭开关（环境变量，例如 `<技能>_JOURNEY=off`）；SKILL.md 写明用户问起时如实说明收集了什么、怎么关；
    - 开发和测试时 `is_test=true`，不污染正式数据。

## 二、决策关口（必须停下等负责人确认）

| 关口 | 时机 | 需要确认的内容 |
|---|---|---|
| ⛔ G1 立项 | 阶段 1 结束 | 立项单全部内容，含核心词与词表初稿、技能 name（有含义的英文）；已读 WorkBuddy 官方文档的记录（第〇章）；本技能的漏斗步骤对应表（第六章） |
| ⛔ G2 计费 | 阶段 2 结束 | 计费单位、各项单价、免费策略（默认没有）、哪些情况不收费 |
| ⛔ G3 供应商 | 阶段 3 结束 | 选定的数据供应商、套餐和实际额度、单次成本、盈亏线；负责人负责注册和订阅 |
| ⛔ G4 上架 | 阶段 7 结束 | 上架包、上架文案、自查清单结果、面向用户文字的逐句检查结果（固定规则第 10 条）、零消耗验证结果、对照 WorkBuddy 官方文档的字段与目录核对结果、开口统计与漏斗验收结果（第六章） |

确认时把要确认的内容整理成简短清单发给负责人，写清「需要你确认」。负责人没有明确回复，不得继续。

## 三、流程阶段

| 阶段 | 产出 |
|---|---|
| 0 复盘（有旧包或竞品时） | 问题清单、转化漏斗 |
| 1 立项 | 立项单 → ⛔ G1 |
| 2 计费设计 | 计费方案 → ⛔ G2 |
| 3 数据供应商选型 | 选型结论、成本与盈亏线 → ⛔ G3 |
| 4 接口约定与后端开发（Codex） | 完整规格文件、Codex 交付报告 |
| 5 客户端技能包 | SKILL.md、脚本、references |
| 6 测试 | 模拟后端和端到端检查全部通过 |
| 7 上架准备 | 上架包、Skill-SEO 文案、自查清单、零消耗验证 → ⛔ G4 |
| 8 上线监控与迭代 | 每日数据、两周复盘 |

### 阶段 0：复盘

- 完整阅读旧包：SKILL.md、脚本、**数据实际来自谁的接口**、计费方式、话术。
- 用上架后台数据和首次对话上报算漏斗：下载 → 首次对话 → 免费体验 → 开通 → 打开充值页 → 付费成功；算每步转化率和客单价，**先解决流失最大的一步**。（外贸获客旧版：下载到开通只有 6%，原因是看到真实结果前就要求开通。）
- 产出按严重程度排序的问题清单。

### 阶段 1：立项单（⛔ G1）

```
技能名称（中文）：
技能标识：mps-
目标用户：
核心价值（一句话）：
用户输入：
输出：（对话内展示什么、导出什么文件）
数据来源：（需要哪些外部接口）
计费单位候选：
免费策略：默认无（例外需说明理由）
首次对话上报：必做（固定规则第 12 条）；其他数据统计默认不做
核心词与词表初稿：（核心词 1–2 个、同义词、用户原话，按第五章第 2 节）
合规风险：（数据来源、个人信息、平台条款）
参考的旧包或竞品：
```

**SEO 从立项开始做，不留到上架**：立项时就定核心词和词表初稿（第五章第 2 节），技能名称、name、description 都按词表起；阶段 5 写 SKILL.md 时 description 直接按第五章写好（含用户原话、触发词、调用倾向句）；阶段 7 只做核对和上架页同步，不在上架时临时补写。

### 阶段 2：计费设计（⛔ G2）

- **按用户能理解的有效结果计费**（一次搜索、一家公司、一位联系人），不按接口调用次数计费。
- 列出每个计费项和默认单价（单位：分），后台可配置。
- 列出所有**不收费**的情况（见固定规则第 8 条）。
- **免费体验放在用户能看到真实价值的位置**，并尽量不要求先登录（外贸获客：每天 1 次免费搜索，未登录可用，按设备和账号双维度计数，另加 IP 上限防刷）。
- 防超支：支持用户设定费用上限（例如 `--budget`），到上限先停下导出已完成部分。

### 阶段 3：数据供应商选型（⛔ G3）

- 评估五项：**接口覆盖**（是否一家包全所需接口）、**实时性**（对话场景要求几秒内返回）、**价格**、**稳定性**（订阅数、评分、可用率、响应时间）、**合规风险**。
- **必须看到套餐页的实际额度再算成本**：credits 和 requests 是两个不同的上限；硬上限还是超额收费要看清。不得用第三方文章里的价格（外贸获客第一次估算就因此偏差很大）。
- 算**单次成本**和**盈亏线**：月固定费 ÷ 单笔毛利 = 每月需要卖出的量。
- 准备一家**按量付费、无月费**的备用供应商（先写骨架）。
- **免费额度全部留给真实用户**，开发和测试一律不调用真实上游。
- 第三方平台注意：页面上的 AI 助手、Run / Test Endpoint 按钮会真实调用并扣额度；示例响应只在文档页查看。

### 阶段 4：接口约定与后端开发（Codex）

**开口统计与漏斗的服务端要求按第六章第 2 节写进规格，必做。**

**把全部要求写成一份完整规格文件，放进 Codex 的工作目录**（`Codex完整规格_<技能名>.md`），并附上供应商的名称和文档链接。只在对话里发过的指令 Codex 看不到。规格分三部分：

**第一部分：平台接入**

- 通用付费页按 skill 参数显示；技能配置集中管理（标题、简介、钱包类型、档位、单价、每日免费次数）；
- 人民币钱包 + 流水表；`(账号, 幂等键)` 唯一；扣费原子化，余额不能为负；
- 支付回调按订单上的 skill 入账，回调幂等；
- 不得影响 Temu 独立付费页、其他技能的付费页和生图技能的 token 扣费。

**技能端接口约定**（客户端和服务端共用）：

- 鉴权：`POST /auth/start` → 浏览器打开 `login_url` 确认 → `POST /auth/poll` 拿 token；失效返回 401 `INVALID_TOKEN`；
- 查询：`GET /pricing`（不用登录）、`GET /me`（余额、今日免费次数、充值链接）；
- 业务接口：每个可能扣费的 POST 必须带 `Idempotency-Key`；响应带 `billing: {charged_fen, balance_fen, free_trial}`；
- 余额不足：402 `INSUFFICIENT_BALANCE`，附 `recharge_url`；
- **幂等只缓存成功响应**（2xx 和「档案缺失」这类确定结果）；402、401、429、5xx 不缓存；
- 扣费放在拿到上游成功结果之后、返回之前，与写流水同一事务；
- 统一错误格式 `{"error": {"code", "message"}}`，错误码列表固定。

**第二部分：数据供应商适配层**

- 适配接口统一封装，供应商通过环境变量切换；先实现 MockProvider；
- 字段映射用文档页的示例响应做 fixture，映射要容错；
- 缓存：按查询参数缓存，命中缓存照常向用户计费、不消耗上游额度；
- 上游调用表：供应商、接口、是否命中缓存、状态码、耗时、剩余额度；管理端按天汇总上游调用量、收入、估算毛利；
- 备用供应商骨架，主供应商连续失败时自动切换。

**第三部分：部署**

- Key 只放服务器环境变量；不进代码、日志、报告（报告里只写末 4 位）；提交前 `git grep` 检查；
- **额度保护**：按供应商的计量单位统计（以响应头里的剩余额度为准），接近上限时停止调用上游、返回「服务繁忙」、不扣用户费用；
- 免费额度期间拉长缓存、限制每次查询的调用量（如关键词上限），全部做成环境变量，升级套餐只改变量不改代码；
- **零消耗冒烟测试**：测试账号和测试设备走 MockProvider，计费、免费次数、402、付费页跳转走真实逻辑，报告写明「真实上游调用 0 次」；
- **真实数据回流**：每个接口前 3 次真实响应脱敏存档；映射失败时不扣费并记录原始响应；管理端显示「映射失败次数」。

**交付报告格式**：三部分完成情况；实际接口（**与约定不一致的逐条列出**）；login_url 和付费页链接示例；冒烟测试结果；环境变量清单；已知问题。

Codex 用电脑操作第三方网站时，必须写明禁止点击的按钮（运行、订阅、升级、取消、AI 助手），只许查看。

### 阶段 5：客户端技能包

目录结构：

```
mps-<技能>/
├── SKILL.md
├── README.md
├── _meta.json
├── scripts/
│   ├── <主脚本>.py          # 关联账号、查余额和单价、查询、整理、导出、等待轮询
│   └── welcome_copy.py      # 固定话术（欢迎句、引导语、付费触点、交付文案）
├── references/
│   ├── scenes.md            # 场景路由表（用户需求 → 命令和参数）+ 通用规则
│   └── ...                  # 用法技巧、示例、文案写法等
└── tests/
    └── test_skill_contract.py   # 契约测试，随包分发，解压即可运行
```

**SKILL.md 总体要求**

- frontmatter 的 description 按第五章 Skill-SEO 规范写，末尾带触发词。
- description、README 和对用户说的话术里，严禁出现开发过程的内容（固定规则第 10 条）；给 AI 的执行指令只写在正文执行说明里。
- 固定话术由 `welcome_copy.py` 输出，SKILL.md 要求 AI 原样转述，不得改写。计费说明读取 `status` 的实时单价，不写死金额。付费触点用语：「支付通过微信/支付宝官方通道完成，充值后回来说『继续』即可接着整理。」
- 如实声明（数据来源、覆盖范围、拿不到什么）写进 SKILL.md。
- 每一步按脚本返回的信号和退出码分支处理，并写出对用户说的话。
- 需要用户输入专业参数的地方由 AI 代劳（例如把中文产品名翻成英文品类词、国家名转代码），不让用户自己做。
- 手机端用卡片式列表，不用宽表格；报告全文不贴进对话，只给文件路径和摘要。
- 不向用户暴露错误码、字段名、token 等技术词；链接从脚本输出原样复制，不得手打。
- 篇幅控制在 15KB 以内。

**1. 首用引导：四步有序协议**

首次使用时按顺序走完四步，**不得跳步**：

1. **欢迎句**：固定规则第 1 条，逐字不改。
2. **用法介绍**：能做什么、怎么用，给 2–3 个用户口吻的例子。
3. **免费体验和开通说明**：
   - 有免费体验的技能，先说明免费额度（以 `status` 返回为准），并直接带用户用掉这次免费体验，让用户先看到真实结果；
   - 再说明计费方式：按什么结果计费、单价（读取 `status`）、哪些情况不收费（零结果、档案缺失等）；
   - 「暂时不开通也没关系。」
   - 频次类钱包按技能独立，**不写跨技能共享的说法**。以后改为共享，须经负责人确认后再加。
4. **给开通链接**：在免费体验用完、或用户要继续使用付费功能时给出。

规则：

- 不得跳过用法介绍直接给链接，也不得跳过用法介绍直接谈钱。
- **首轮要快**：首轮的任务是尽快让用户拿到第一份真实结果（有免费体验时）或入口（无免费体验时），不做方案确认；确认放在付费动作之前。
- **拒绝分支**：用户说先不开通，只回一句「没问题。等你需要的时候随时叫我。」然后结束。不再推销、不追问、不重发链接。
- **引导边界**：完整的能力介绍只在两种情况出现：首次使用、用户主动问能做什么。开通和充值流程中途不插入介绍。

**2. 付费动作前两次确认**

1. **方案确认**：查询条件（产品、国家、范围等）和要整理的对象（例如先展示清单，问整理哪几家）。
2. **提交前一句话复述**：查什么、范围、预计结果数量、单价（以 `status` 为准）和预计费用或费用上限。**内容缺一不可**，用户明确同意后才提交。

免费体验那一次豁免两次确认（见上一节）。

**3. 等待管理**

- **外层超时按最慢接口的实测时长留足余量**，SKILL.md 命令表和 `references/scenes.md` 两处都写明同一个数值。
- 提交前按任务大小（例如整理几家）给出等待预估。
- 批量任务每完成一项报一次进度，进度信息走 stderr，分段播报给用户。
- 后端是异步任务时，客户端进入等待轮询（参考：每 30 秒一次，最多 5 轮）；轮询结束仍未完成，告诉用户任务已保存，稍后说「继续」即可接着查，不重复扣费。
- **轮询和重试不得吞掉异常后报「仍在处理」**。脚本要分别记录请求次数和成功拿到应答的次数：
  - 拿到过应答、状态还是处理中 →「仍在处理」；
  - 一次都没连上 →「当前进度未能确认」，不得说「仍在处理」；
  - 明确失败 → 按失败处理，不扣费。
- 等待期间不得换参数重新提交：同一任务用同一幂等键续查不重复扣费，换了参数就是新任务、会重新计费，这一点写进脚本输出。

**4. 结果与交付**

- **结果数量如实告知**：实际结果比用户要的少时（例如要 20 家，只找到 8 家），直接说明，并给出放宽条件的建议。
- **只展示接口真实返回的数据**：联系人、邮箱、电话、职位等不得补全或编造；拿不到的字段写「未获取到」。
- 参数报错时点名是哪个参数、什么问题。
- **服务端支持的参数和范围以服务端实际支持为准**（固定规则第 11 条）；未经确认的参数在 SKILL.md 标注「待服务端确认后再放开」，不得先对用户承诺。
- 导出文件给出路径和摘要；同一任务的多轮结果分开保存。
- 用户要调整时，引导「每次只改一个条件」，这句写进 SKILL.md 和 `scenes.md`。

**5. 场景路由**

- `references/scenes.md`：路由表（用户需求 → 命令和参数）和通用规则。
- **场景点名制**：每次调用先说明走的是哪个场景，不得临时自由组合参数。
- 生成类内容（例如开发信）只用接口返回的事实和用户提供的信息，不夸大、不编造合作或资质。

**6. 脚本要求**

- 仅用 Python 3.7+ 标准库。
- **退出码**：0 完成；2 等待用户动作（登录、充值、换词、确认），不是失败；3 错误。
- **首次对话上报**按固定规则第 12 条在第一轮由脚本完成，关联账户后补调 `/first-dialogue/link`；上报失败不影响主流程。
- **stdout**：一行 JSON 信号，供宿主 AI 判断下一步（例如 `freeTrial` 免费体验、`needsLogin` 需要关联账号、`needsCredits` 需要充值、`jobPending` 仍在处理），后面跟 `welcome_copy.py` 输出的固定话术。话术放在脚本里，是为了逐字稳定、能被测试锁住。
- **stderr**：只放进度信息。
- 本地状态放 `~/.<技能>/`，凭据文件权限 600，模型不得读取。
- **断点续查**：每完成一项保存一次进度；同一项的同一动作使用固定幂等键，重跑和充值后续查都不重复扣费。
- 每个任务单独保存进度，换参数不覆盖上一轮。
- 临时性错误（429、5xx、网络）用同一幂等键自动重试最多 2 次。
- 导出文件不覆盖已有文件；CSV 用 UTF-8 BOM，Excel 直接打开不乱码。
- **契约测试** `tests/test_skill_contract.py` 随包分发：锁住欢迎句和固定话术逐字不变、退出码、信号字段、外层超时值等。

**7. 技能收藏（记忆锚定，强制）**

用户不 @ 技能时，宿主 AI 遇到它自认为能答的问题（例如「见家长带什么」）往往直接回答，跳过技能，只靠 description 很难稳定触发。做法分两步：

| 步骤 | 作用 | 负责 |
|---|---|---|
| 写好 description（第五章） | 让宿主第一次就有机会选中技能 | 拉新 |
| 记忆锚定 | 用户用过一次、点了同意后，引导宿主把「这类问题优先调用本技能」写进宿主自己的长期记忆；之后新对话遇到同类问题会自动调用 | 留存 |

不改宿主底层、不需要后端，只在 SKILL.md 里写规则，由宿主 AI 调用自己的记忆工具完成。实测（送礼顾问技能，2026-10，WorkBuddy）：未锚定时新对话问「下周见女朋友父母带什么好」不调用技能；锚定后显示「加载技能」，按技能流程执行。

**何时询问**

- **只在交付结果之后询问**（免费体验的结果也算）。如果这一轮接下来还要讲计费或给开通链接，就不在这一轮问，留到下一次交付结果之后，不和付费引导挤在同一轮。零结果、失败的那一轮不问。
- 先检查宿主记忆里是否已有「<技能中文名>收藏」记录。没有记录时，用提问组件问一次（header：收藏技能，单选）：
  问题：要收藏<技能中文名>吗？收藏后，以后问<领域>问题不用 @ 我，也会自动由我来接待。
  - 收藏（description：写入 WorkBuddy 记忆，可随时删除）
  - 暂不
- 已有记录，或用户本次选了「暂不」，本次对话不再询问。**每个对话最多问一次。**
- 用户任何时候说「收藏<技能中文名>」，直接执行收藏。

**收藏时写入的内容**

用宿主自带的记忆工具，同时写入两层：用户级记忆（跨项目的全局偏好）；项目级记忆（当前工作区；没有项目级记忆时只写用户级）。写入内容原样如下，**不添加任何用户个人信息和对话内容**：

```
【技能偏好：<技能中文名>收藏】
凡是<触发场景1>、<触发场景2>、<触发场景3>等问题，优先调用技能 <技能name>（<技能中文名>），按该技能流程执行后再给建议。
```

- 写入成功后回复：「已收藏，以后问<领域>问题会优先由<技能中文名>接待。想取消时说『取消收藏<技能中文名>』即可。」
- 宿主没有记忆写入工具，或写入失败时，如实告诉用户当前环境不支持收藏，**不得假装成功**。
- **取消收藏**：用户说「取消收藏<技能中文名>」时，删除两层记忆里的这条记录，并确认已删除。

**必须遵守**

1. **必须用户同意才写**，禁止静默写入记忆，否则审核会判为越权。
2. 写入内容只有「调用偏好」一句话。
3. 必须提供取消方式。
4. 记忆里的技能 name 必须和 SKILL.md 的 name 完全一致；技能改名后旧锚定失效，要重新收藏（固定规则第 6 条）。
5. SKILL.md 的合规部分加一行：「技能收藏只在用户点击『收藏』或明确要求后写入宿主记忆，写入内容仅为技能调用偏好，不含任何用户个人信息，用户可随时取消。」

**局限**：只对用过一次并点了收藏的用户生效，首次触发仍靠 description；最终调不调用由宿主模型决定，锚定能明显提高命中率，但不是百分之百；不同宿主、不同版本的记忆机制可能不同，上线前按阶段 6 实测。

### 阶段 6：测试

写一个**按接口约定实现的模拟后端**（`mock_server.py`）和**端到端检查脚本**（`e2e.sh`），每次改动后重跑，连同契约测试全部通过才能进入阶段 7。必测场景：

**账号与计费**

- [ ] 免费体验（未登录）成功
- [ ] 免费次数用完 → 要求关联账号
- [ ] 关联账号：等待确认 → 确认后成功
- [ ] 登录后正常扣费
- [ ] 零结果不扣费、不占免费次数
- [ ] 中途余额不足 → 402，进度已保存，充值链接带 skill 参数
- [ ] 充值后同一命令续查，不重复扣费
- [ ] 档案缺失跳过、不扣费、保留线索
- [ ] 已完成的任务重跑不再扣费
- [ ] 费用上限生效
- [ ] token 失效自动清除并提示重新关联

**引导与确认**

- [ ] 首用四步按顺序出现，欢迎句逐字一致
- [ ] 用户拒绝开通 → 只回固定一句后结束，不重发链接
- [ ] 付费动作前两次确认齐全，复述内容不缺项

**等待与重试**

- [ ] 一次就返回
- [ ] 临时错误后自动重试成功，不重复扣费
- [ ] 异步任务轮询结束仍未完成 → 提示稍后继续，进度已保存
- [ ] 全程连不上 → 说「当前进度未能确认」
- [ ] 明确失败 → 不扣费

**交付**

- [ ] 参数不合规在本地拦截，不调用服务，报错点名具体参数
- [ ] 结果少于预期时如实告知
- [ ] 拿不到的字段显示「未获取到」，不编造
- [ ] 导出文件存在且不覆盖
- [ ] 首次对话上报只含白名单字段、每个安装只发一次、失败不影响第一轮、关闭开关生效；关联账户后 link 调用成功；开口统计按第六章第 5 节验收

**技能收藏（记忆锚定）**

- [ ] @ 技能完整走一次，交付后弹出收藏卡片；付费或购买流程中途不弹
- [ ] 点「收藏」后，宿主记忆管理里用户级和项目级各有一条记录，内容只有调用偏好一句话
- [ ] 选「暂不」后，本次对话不再询问
- [ ] 开新对话，不 @ 技能，直接问一句该领域的问题 → 出现「加载技能 <技能name>」，并按技能流程执行
- [ ] 说「取消收藏<技能中文名>」→ 两层记忆里的记录都被删除
- [ ] 宿主不支持写记忆时，如实告知不支持，不假装成功

模拟后端和检查脚本交给 Codex，用来验证服务端与客户端兼容（不得消耗真实额度）。

### 阶段 7：上架准备（⛔ G4）

- **零消耗验证**（负责人操作）：浏览器打开 `/pricing` 确认单价、免费次数、档位与客户端读取的字段一致；在供应商后台核对 Key 末 4 位。
- 上架包：`mps-<技能>-<版本>.zip`，直接上传，不用解压。
- 上架文案按第五章写，过一遍自查清单。
- 保留上一版上架包，用于回滚。

### 阶段 8：上线监控与迭代

宿主（如 WorkBuddy）版本更新后，重跑一次技能收藏的测试步骤，确认记忆锚定仍然生效。

上线后头几天每天看三个数：

1. **映射失败次数**：不是 0 就把存档的原始响应拿来修映射，当天修好；
2. **供应商额度用量**：用到一半左右时决定是否升级套餐；
3. **收入与固定成本**：月流水超过供应商月费才升级。

升级套餐只改环境变量（额度上限、单次成本、调用量限制）。

每两周按第五章第六节复盘一次上架文案。

**版本号**：功能大改升主版本（2.0.0），修映射、改话术升修订号（2.0.1）。

**回滚**：技能包重新上传上一版；后端按版本目录切回上一版（数据库迁移要可回退）。回滚前告知负责人。

## 四、踩坑记录

| 问题 | 结论 |
|---|---|
| 首次开口上报挂在走不到的分支上，漏斗第一步一直是 0 | 第一轮由脚本主动发，提前返回的分支返回前都要已发出；上线第一天确认数据进来 |
| 标识写不进去时临时造一个，同一台机器被算成很多新设备 | 写不进就跳过这次上报，不临时造标识 |
| 只看单日报表，以为转化很低 | 跨日充值会被单日报表漏掉，看 7 天以上窗口 |
| 凭记忆或只按 SOP 摘要开发 WorkBuddy 包，字段或目录与官方要求不符，提交后解析失败 | 每次开工先读 WorkBuddy 官方开发文档线上最新版，冲突时以官方为准 |
| 用户不 @ 技能时，宿主自认为能答就直接回答，技能没被调用 | description 写用户原话加调用倾向句；用户用过一次后，经同意做技能收藏（记忆锚定） |
| 静默把调用偏好写进宿主记忆 | 必须用户点「收藏」才写，否则审核判为越权 |
| 把和 AI 的开发对话、修改原因写进了上架简介和 description | 原则性错误。面向用户的文字只写用户需要知道的，上架前逐句检查 |
| 指令只发在对话里，Codex 找不到 | 合并成一份完整规格文件，放进工作目录，附供应商文档链接 |
| 幂等缓存了 402，充值后重试一直余额不足 | 只缓存成功和确定性结果 |
| 按第三方文章估算供应商价格，偏差很大 | 以套餐页实际额度为准 |
| 免费版 credits 和 requests 是两个上限 | 额度保护按 credits 计，以响应头剩余值为准 |
| 第三方页面的 AI 助手和 Run 按钮会真实扣额度 | 只看文档示例；让 Codex 操作时写明禁止点击的按钮 |
| 旧版零结果也收费、换词覆盖进度 | 零结果不收费；每个任务单独保存进度 |
| 旧版开通前看不到真实结果，转化只有 6% | 免费体验前置，不登录也能用一次 |
| 跳过用法介绍直接给付费链接 | 首用四步有序协议，不得跳步 |
| 重试吞掉异常，连不上也说「仍在处理」 | 分别记录请求次数和应答次数，一次都没连上就说「当前进度未能确认」 |
| 外层超时太短，任务还在跑就被判失败 | 外层超时按最慢接口实测留足余量，两处写明同一数值 |
| 对用户承诺了服务端没确认支持的参数 | 不推定生产行为，先让 Codex 确认 |
| Claude 的工作环境访问不了 myplanestore 和供应商接口 | 线上验证由负责人用浏览器或由 Codex 完成 |
| 免费服务端可能只取前几个查询词 | 技能里把最重要的词放在最前面 |

## 五、Skill-SEO 规范

### 1. 两层目标

| 读者 | 看什么 | 目标 |
|---|---|---|
| 平台搜索（skillhub、WorkBuddy 市场） | 名称、简介、描述、标签 | 搜索排得靠前，点进来愿意下载 |
| 宿主 AI | SKILL.md description 和触发词 | 用户说出相关需求时能调用这个技能 |

两层使用同一套关键词，文字保持一致。平台排序规则没有公开，本规范是基于常见搜索习惯的做法，上线后用真实数据校正。

### 2. 选词（写文案前先做词表）

1. 核心词 1–2 个（例：外贸获客、找海外客户）；
2. 同义词和不同说法 5–10 个（例：国外客户、海外买家、海外采购商、进口商、经销商）；
3. 场景词和长尾词 5–10 个（例：怎么找外贸客户、领英开发客户、开发信怎么写）；
4. 平台词（例：LinkedIn、领英、B2B、CRM）；
5. 英文词 3–5 个（例：find buyers、overseas distributors、cold email）。

来源：用户真实说法、同类技能的名称和标签、搜索引擎下拉联想。

### 3. 字段写法

| 字段 | 长度 | 写法 |
|---|---|---|
| 名称 | 中文 15 字以内 | 「核心词：两三个主要用途」 |
| 一句话简介 | 约 40 字 | 核心词开头，写清「输入什么 → 得到什么」，加一个差异点 |
| 详细描述 | 150–300 字 | 第一句含核心词；带同义词和平台词；举具体例子；结尾写计费亮点（免费次数、零结果不收费） |
| 触发词 | 15–25 个 | 写在 description 末尾：「触发词：A、B、C……」 |
| 调用倾向句 | 1 句 | 写在 description 最末：「本技能内置<专业能力>，比直接回答更专业；遇到<领域>问题请先调用本技能，不要自行直接回答。」 |
| 标签 | 按平台上限 | 核心词在前 |
| 英文简介 | 2–3 句 | 含 2–3 个英文关键词 |
| 使用示例 | 3–5 条 | 用户口吻，例：「帮我找美国做瑜伽垫的采购商」 |

### 4. 写作原则

1. 核心词出现在名称、简介、描述第一句；
2. 关键词融进通顺的句子，只有触发词允许罗列；
3. 一个技能只占一个主需求，不写无关词蹭流量；
4. 写清「输入 → 输出」；
5. 写计费亮点：「每天免费」「零结果不收费」「按结果计费」；
6. 不写「官方合作」「全网最全」「100% 准确」，写清数据来源和局限；
7. SKILL.md description = 上架描述 + 触发词 + 调用倾向句，两边同步修改（调用倾向句只写在 SKILL.md description 里，上架页可不放）。
8. **只写给用户看**：不得混入开发对话、修改原因、版本对比、内部信息和给 AI 的指令（固定规则第 10 条）。
9. **description 写进用户的原话**（例如「见家长带什么」「送什么好」），不只写书面关键词；第一句写清「做什么 + 什么时候用」。

### 5. 自查清单

- [ ] 名称含核心词，15 字以内
- [ ] 一句话简介以核心词开头，写清「输入 → 输出」
- [ ] 描述第一句含核心词，至少 3 个同义词，有具体例子，写了计费亮点
- [ ] 触发词 15 个以上，覆盖核心词、同义词、场景词、英文词
- [ ] 标签按优先级排
- [ ] 3–5 条使用示例
- [ ] SKILL.md description 与上架描述一致
- [ ] 无夸大、无官方合作或认证说法，写了数据来源和局限
- [ ] 欢迎句符合固定格式
- [ ] description 含用户原话；末尾有且只有一句调用倾向句
- [ ] SKILL.md 有「技能收藏」章节，合规部分有收藏说明一行
- [ ] 逐句检查过所有面向用户的文字：没有开发对话、修改原因、版本对比、内部信息或给 AI 的指令

### 6. 上线后优化

每两周复盘一次：

- 收集用户实际说法，补进词表和触发词；
- 看漏斗：曝光低 → 关键词不对；详情页访问多、下载少 → 简介没讲清价值；下载多、首次使用少 → 触发词不够或首次门槛高；
- 每次只改一个字段，看一周再改下一处，记录修改日期。

## 六、开口统计与转化漏斗（强制，新技能必须严格执行）

**为什么要做**：用户第一次在对话里用技能（首次开口）完全发生在用户本机，以前后台看不见，「下载 → 首次开口 → 激活 → 付费」里最前面的一段是盲区。首次对话上报把这一步变成可统计的指标。**新技能不接这套统计，不得上架。**老技能升级时一并补上。

### 1. 客户端上报规范

1. **两个标识**，都是本机随机生成的**规范小写 UUIDv4**：
   - `installation_id`：每个技能、每次安装一份，存在技能目录里；
   - `machine_id`：每台机器一份，存在我们自己的目录（例如 `~/.mps/machine-id`），只在我们自家技能之间共用；不读取硬件信息，不是设备指纹。
2. **标识文件的处理**：文件不存在、内容损坏（不是规范 UUIDv4、或有乱码）时，原地重新生成并写回；**写不进去就跳过这次上报**。绝不在进程里临时造一个标识凑数，否则同一台机器会被算成无数个新设备，把漏斗数据搞乱。
3. **上报内容**：固定规则第 12 条的字段，`skill_id` 为 kebab-case、不超过 64 个字符。字段名、大小写、格式和服务端白名单完全一致，多一个字段整条会被拒。
4. **只发一次**：每个安装成功发出后，在本地写一个标记，之后不再发。服务端按 IP 每天有上限，同样的内容重发不会被合并，每次都占额度。
5. **发送时机**：第一轮由脚本主动发出，**不能挂在可能走不到的分支上**。首轮示例命令、无凭证预览退出这些会提前返回的分支，返回前都要已经发过。
6. **不打扰主流程**：有界超时（2–3 秒）、不重试、失败静默放弃，不影响业务输出和退出码。上报域名固定在白名单里，环境变量改不了。
7. **接到账户上**：账户关联时，把 `installation_id`、`machine_id`，以及装机渠道、运行环境（只按操作系统区分电脑本机、手机本机、云端沙箱）一起带给服务端。服务端不认这些可选字段时，去掉后用同一个幂等键重发一次，保证关联本身不受影响。
8. **开关与披露**：按固定规则第 12 条提供关闭开关，在 SKILL.md 里披露；开发和测试时 `is_test=true`。

### 2. 服务端规范（写进阶段 4 给 Codex 的规格）

1. **上报接口**：匿名，不要凭证，成功返回 204；请求体严格白名单（多字段即拒）；每个 IP 每天上限 50 次（数值后台可配）；校验两个标识必须是规范小写 UUIDv4。
2. **事件表**：至少包含 `id`、`skill_id`、`installation_id`、`machine_id`、`ip_day_hash`、`occurred_at`。`ip_day_hash` 是 IP 按日加盐的哈希，**不存明文 IP**；明细保留 180 天。
3. **安装或关联表**加 `installation_id`、`machine_id` 两列，用来把首次开口和账户串起来。
4. **上线顺序**：服务端数据库迁移和接口先上线、在测试环境验证通过，再发布带上报的客户端。迁移没装的环境，漏斗按 0 计，不报错。
5. **管理台**：漏斗接口和每一步的明细下钻接口（L0 明细一行一台新设备，不返回 `ip_day_hash`）；另附一个和管理台同口径的离线报表脚本，两边数字必须一致。

### 3. 转化漏斗口径（只统计新用户）

漏斗只看新用户。老账户装新技能不算进漏斗，用下面第 4 节的独立指标看。

| 步骤 | 口径 | 数据来源 |
|---|---|---|
| L0 首次开口（新设备） | 窗口内首次出现的 `machine_id`：该机器历史上第一条首次对话上报落在窗口内 | 首次对话上报事件表 |
| L1 用掉免费体验（新设备） | 窗口内新设备第一次成功使用免费体验（零结果不算） | 免费次数记录 |
| L2 打开授权页（新访客） | 授权页的页面访问事件中，`ip_day_hash` 历史首现落在窗口内；PV 只数匿名访问，UV 按哈希去重 | 页面访问事件表 |
| L3 完成授权（新账户） | 窗口内新建、且首次关联的账户 | 账户表、设备关联表 |
| L4 打开充值页（新账户） | 充值页到达事件，经设备凭证对应到账户；只算账户创建时间落在窗口内的；按账户去重 | 充值页访问事件 |
| L5 首充成功（新账户） | 窗口内新建账户的第一笔人民币钱包入账：支付订单入账和未挂订单的账本充值逐条去重，按账户取最早一笔 | 订单表、资金流水表 |

技能没有免费体验时去掉 L1，其余顺延。我们的流程没有「在对话里提交手机号」这一步（方案 A）。

**时间窗口**：按北京时间自然日。查询某一天 D，从 UTC 的 D-1 日 16:00 起，到 UTC 的 D 日 16:00 止；按天数查询时用 UTC 滚动窗口。

**注意跨日低估**：账户 D 日创建、D+1 日才充值，单日报表里不会算进首充，所以**单日报表会系统性低估转化**。判断转化率看 7 天以上的窗口。

### 4. 三个独立指标（和漏斗分开看）

| 指标 | 管理台名称 | 口径 |
|---|---|---|
| 技能启用数 | 技能启用数 | 窗口内 `installation_id` 历史首现的个数，按技能分组；按这台机器是不是窗口内的新设备，拆成「新设备」和「老设备」。老设备装新技能的首次开口，漏斗 L0 不算，这里算 |
| 技能激活数 | 技能激活数 | 窗口内新增的技能与账户绑定数，拆成「新账户」和「老账户」 |
| 充值笔数 | 充值笔数 | 窗口内全部入账笔数（人民币钱包入账），按支付渠道拆分 |

渠道看板用「技能启用数」除以对应渠道的下载数，算出「下载 → 开口」比值。

### 5. 上线与验收

- **G1**：确认本技能的漏斗步骤怎么对应（上面的表要按本技能实际流程填写），哪些步骤数据不可得。
- **阶段 6**：
  - 用测试账号（`is_test=true`）从首次开口走到首充，管理台每一步都能看到这条测试数据，明细下钻能查到；
  - 标识文件损坏、目录只读、断网时，主流程不受影响，并且不会产生临时标识；
  - 同一安装重复运行只上报一次；
  - 管理台和离线报表脚本的数字一致。
- **G4**：提交上面的验收结果。
- **上线第一天**：确认正式数据开始进入；如果是 0，先查服务端迁移是否已装、客户端是否真的发出，不要等。
- **阶段 8**：每天看 L0 到最后一步的漏斗和三个独立指标；哪一步流失最大，先改哪一步。
