# 通用生图类 Skill 开发 SOP

本 SOP 适用于**生图类付费 Skill**：用户提供图片或需求，技能调用后端生图，按张扣 **token**，付费走 myplanestore.com。

- 按次或按结果计费、调用外部数据接口的技能 → 用「频次类 Skill 开发 SOP」。
- 全免费的技能 → 不适用本 SOP，按负责人开发时的说明临时调整。
- 拿不准属于哪一类 → 先问负责人，不要自行判断。

**执行要求：严格按阶段顺序推进。每个阶段的产出齐了才进入下一阶段。遇到「⛔ 决策关口」必须停下，等负责人明确确认后才能继续。不得跳过阶段，不得自行放宽固定规则。**

**所有 WorkBuddy 开发工作开工前，必须先读取 WorkBuddy 官方开发文档**，包括新开发、重构、优化、修 bug、改文案、打包上架。

1. **必读入口**：https://open.workbuddy.cn/docs/expert （专家），并按要做的产品类型读对应页面：
   - 技能：https://open.workbuddy.cn/docs/skill
   - 专家团：https://open.workbuddy.cn/docs/expert-team
   - 连接器：https://open.workbuddy.cn/docs/connector
   - 开放平台操作指引：https://open.workbuddy.cn/docs/what-is-open-platform
2. **每次开工都重新读线上最新版**，不凭记忆、不只读本 SOP 里的摘要。读完在工作记录里写一行：「已读 WorkBuddy 官方文档（日期、读了哪几页）」。
3. **官方文档优先**：本 SOP 与官方文档冲突时，以官方文档为准，先停下报负责人，确认后再改本 SOP。
4. 读不到文档（网络受限、页面改版）时，停下告诉负责人，不得按记忆继续开发。
5. 官方文档没写清的问题（例如字段长度、审核标准），不推定，发邮件问 openworkbuddy@tencent.com 或在开放平台社群里问，答复记进踩坑记录。

**官方要点摘要（2026-11-04 阅读；只作索引，以线上文档为准）**

- **技能包**：目录为 `SKILL.md`（必须）+ `references/`、`scripts/`、`templates/`（可选）；正文里用 `@references/xxx.md` 引用参考资料。frontmatter 必填：`name`、`display_name`、`display_name_en`、`description`（用途和触发词）、`description_zh`（详情页中文简介）、`description_en`、`version`、`author`（合作方名称）；可选 `allowed-tools`（工具白名单）、`examples_zh` / `examples_en`（详情页「试试这样用」）。
- **专家包**：目录为 `.codebuddy-plugin/plugin.json`、`avatars/`、`agents/<name>.md`、`README.md`。`plugin.json` 必填 `name`、`expertType`（agent / team）、`version`（语义化版本）、英文 `description`、`author`（name、email）、`agents`、`agentName`；展示字段全部必填：`displayName`、`profession`、`displayDescription`（中英，**中文 40–50 字**）、`avatar`、`categoryId`（15 个行业分类之一）、`plugin`（与 name 一致）、`defaultInitPrompt`（**必须和 quickPrompts 第一条一致**）、`tags`（**正好 3 个**）、`quickPrompts`（**正好 3 个**）。专家团另需 `teamInfo`（leadAgent、memberAgents）。
- **Agent 定义文件**（`agents/*.md`）：frontmatter 必填 `name`、`description`、`displayName`、`profession`，可选 `maxTurns`（默认 50）、`skills`；正文就是系统提示词。**开发者不能自己加工具**，工具由系统分配。
- **依赖**：MCP 和连接器在 `plugin.json` 的 `dependencies` 里声明（或根目录 `.mcp.json`），认证方式为 oauth / token / none；token 用表单和 `${VAR}` 占位，**禁止在包里硬编码真实 token 或 Key**。
- **头像**：PNG（优先）或 JPG，512×512 像素，不超过 500KB，放在 `avatars/`。
- 提交 zip 后解析失败时，先对照官方目录结构和字段说明排查；官方提供专家模板 `design-experts.zip`。
- 入驻流程：注册入驻 → 资质认证 → 创建业务类型 → 完善信息和能力配置 → 提交审核 → 发布上线 → 运营和版本维护。

## 一、固定规则（不得修改）

1. **欢迎句固定**：「欢迎使用WorkBuddy官方认证技能 <技能名>。」只替换末尾技能名，其余一字不改。
2. **付费只走 myplanestore.com**，不使用 AISkill 或任何其他平台的计费。
   - 通用付费页：`https://myplanestore.com/pay?skill=<后端技能标识>`，页面按 skill 参数显示本技能的标题和档位；
   - **Temu 两个 WorkBuddy 版本（专家包、技能包）使用独立付费页**；其他所有生图技能一律走通用付费页；
   - 通用档位：¥29 / ¥49 / ¥99。
3. **钱包**：生图类技能扣 **token**。每张图消耗多少 token（例如按分辨率区分）以后台配置为准，SKILL.md 和话术里不写死数值。
4. **免费试用默认没有**。唯一例外是 Temu 两个版本：新用户免费 1 次，相关文案必须保留。新增例外必须经负责人确认。
5. **账号关联用方案 A**：网站记住浏览器登录态，WorkBuddy 新对话通过设备关联链接回原账号；专家包和技能包都适用。不得在对话里索要手机号、验证码、密码或支付信息。
6. **发布渠道**：WorkBuddy 团队版的「专家」和「技能」两个渠道，以及 skillhub.cn。同一产品出两个包时，计费、话术、欢迎句保持一致。
7. **技能标识**：新技能统一使用 `mps-` 前缀，后面用**有含义的英文**，不用拼音（例：`mps-gift-advisor`，不用 `mps-songli`）。更换标识等于新的上架条目，旧条目的下载量不会继承，用户已做的技能收藏（记忆锚定）也会失效；改名前先告知负责人。
8. **如实声明**：AI 生成、可能与实物有差异、平台审核以平台为准，这些要写进 SKILL.md 和上架文案。不得宣称官方合作、认证或「100% 过审」。
9. **事实不编造**：产品名称、尺寸、材质、卖点、产品上印的文字，只用用户提供的。缺什么就问，或者跳过对应的图，不得猜测。
10. **面向用户的文字里，严禁出现开发过程的内容（原则性错误）**。面向用户的文字包括：上架名称、一句话简介、详细描述、触发词、标签、使用示例、英文简介、SKILL.md 的 description、README，以及 SKILL.md 里让 AI 对用户说的话术。这些文字只写用户需要知道的：能做什么、怎么用、怎么收费、有什么局限。严禁出现：
   - 负责人和 AI 的对话内容，以及「按你说的」「已确认」「已改为」「G2 通过」这类开发过程用语；
   - 修改原因和版本对比，例如「相比旧版」「修复了……」「新版改为……」「旧版转化只有 6%」；
   - 内部信息：SOP 阶段和关口、踩坑记录、成本、毛利、供应商额度、后端接口、字段名和错误码；
   - 写给 AI 的执行指令（例如「不要编造」「先调用 status」「必须征得确认」）。这些只能写在 SKILL.md 正文的执行说明里，不得写进 description 和上架文案。

   **唯一例外**：description 末尾、触发词之后，允许一句固定格式的「调用倾向句」（见第五章），这是让宿主不 @ 也能选中技能的必要写法，不算违反本条。除这一句外，description 里不得出现其他给 AI 的指令。

   写完后逐句检查：一个第一次看到这个技能的用户读到这句话，是否需要、是否看得懂。不是，就删掉。
11. **不推定生产行为**：服务端支持什么（参考图格式、尺寸、等待时长等），以服务端实际确认为准。没确认的能力不写进对用户的承诺，交给 Codex 确认后再放开。
12. **用户数据统计（遥测）只做「首次对话上报」一项，且必须做**。其他任何统计默认不做，要做必须负责人确认，并在 SKILL.md 和上架文案里明示收集什么。首次对话上报的统一做法：
    - 走服务端既有协议 `POST /platform-api/telemetry/v1/first-dialogue`，由脚本在第一轮完成，**每个安装只发一次**（本地写标记），有界 2 秒、不重试、失败即弃，不阻塞也不拖慢第一轮，不靠宿主调用；
    - 只报 9 个字段：`event_id`、`installation_id`、`machine_id`、`skill_id`、`skill_name`、`skill_version`、`channel`、`client_occurred_at`、`is_test`（`machine_id` 须等服务端白名单加上后才发，见第六章）；**不含用户原话、提示词、图片、账户或手机号**；服务端字段白名单严格，多一个键整条返回 400；
    - 两个标识都在本机随机生成：`installation_id` 每个技能每次安装一份；`machine_id` 每台机器一份，**只在我们自家技能之间共用**，不从硬件、MAC 地址、序列号等推导，不是设备指纹；服务端按「安装标识 × 技能 × 渠道」去重。完整口径见第六章；
    - 账户关联后调用 `/first-dialogue/link` 接到账户上（幂等），用于计算「首次对话 → 开通 → 付费」转化；
    - 提供关闭开关（环境变量，例如 `<技能>_JOURNEY=off`）；SKILL.md 的合规部分写一句披露（例如「首次对话上报的匿名安装标识仅用于统计使用情况和安装绑定」），用户问起时如实说明收集了什么、怎么关；
    - 开发和测试时 `is_test=true`，不污染正式数据。

| 阶段 | 产出 |

| 1 立项 | 立项单 → ⛔ G1 |
| 2 出图规划与计费设计 | 图位方案、计费方案 → ⛔ G2 |
| 3 模型与后端方案 | 模型选型、成本测算 → ⛔ G3 |

### 阶段 0：复盘

- 完整阅读旧包：SKILL.md、脚本、调用的接口、计费方式、话术。
- 用上架后台数据和首次对话上报算漏斗：下载 → 首次对话 → 认可方向 → 同意付费执行 → 完成授权 → 打开充值页 → 付费成功；算每步转化率和客单价，**先解决流失最大的一步**。
- 产出按严重程度排序的问题清单。

### 阶段 1：立项单（⛔ G1）

填写并发给负责人确认：

技能标识：mps-
发布渠道：专家包 / 技能包 / skillhub（可多选）
目标用户：
目标平台和图片规范：（如亚马逊主图、Temu、Shopify）
用户输入：（产品图、文字信息、尺寸……）
输出：（几张图、哪些图位、分辨率、比例）
免费试用：默认无（例外需说明理由）
付费页：通用 / 独立
账户额度是否跨技能共享：

**SEO 从立项开始做，不留到上架**：立项时就定核心词和词表初稿（第五章第 2 节），技能名称、name、description 都按词表起；阶段 5 写 SKILL.md 时 description 直接按第五章写好（含用户原话、触发词、调用倾向句）；阶段 7 只做核对和上架页同步，不在上架时临时补写。

### 阶段 2：出图规划与计费设计（⛔ G2）

- **图位方案**：按目标平台列出每个图位（如主图、卖点图、细节图、场景图、尺寸图、包装清单图）的内容、比例、尺寸、是否带文字、文字语言。
- **平台规范**整理进 `references/platform-rules.md`（白底要求、主体占比、禁止元素、尺寸范围、文字语言）。
- **计费规则**：
  - 一次请求出一张图，多图套装按张分别请求，中途失败只扣已交付的图；
  - **出图成功并交付后才扣费**；生成失败、被内容策略拒绝、上游报错一律不扣；
  - 重新生成要再次扣费，必须先征得用户同意；
  - 免费的检查类操作（例如离线审图）不调用后端、不扣费，应该放在付费出图之前。
- **费用确认话术**：出图前说明张数，并写明「按张计费，以实际账单为准」，拿到明确同意再出图；**对话里不报具体档位和金额**，金额以充值页和服务端为准。并入阶段 5 的「提交前一句话复述」。

### 阶段 3：模型与后端方案（⛔ G3）

- 选模型看四项：产品还原度（形状、颜色、印字是否保真）、文字渲染准确度、速度、单张成本。
- **模型密钥只放在服务端**，技能端不持有任何模型 Key；模型名称不写进技能端接口约定，便于后端换模型不必发版。
- 成本测算：单张模型成本 × 平均每单张数，对比每张 token 对应的收入，算毛利；有月费的服务算盈亏线（月费 ÷ 单张毛利）。

### 阶段 4：后端开发（Codex）

**开口统计与漏斗的服务端要求按第六章第 2 节写进规格，必做。**

**把全部要求写成一份完整规格文件，放进 Codex 的工作目录**（`Codex完整规格_<技能名>.md`）。只在对话里发过的指令 Codex 看不到。规格必须包含：

1. **平台接入**：通用付费页按 skill 参数显示；token 钱包扣费；支付回调幂等；订单记录 skill。
2. **技能端接口约定**：
   - 设备关联：`/auth/start` → 浏览器确认 → `/auth/poll` 拿 token；失效返回 401；
   - `GET /pricing`、`GET /me`（余额、充值链接）；
   - `POST /images/generate`：必须带 `Idempotency-Key`；同一个 key 24 小时内重放返回第一次的成功结果、不重复扣费；
   - **幂等只缓存成功响应**。402、401、429、5xx 不缓存，否则用户充值后用同一个 key 重试会一直余额不足；
   - 余额不足返回 402，附 `recharge_url`（通用付费页 + skill 参数）；
   - 内容策略拒绝返回 422，不扣费；同一个 key 还在生成中返回 409，不扣费；
   - 响应里带本次扣费和剩余余额（客户端原样转述，不自行计算），余额低于后台阈值时带低余额标记；
   - 图片返回直连下载地址（至少 1 小时有效，支持分段下载和断点续传）或 base64；
   - **内联补取**：出图请求支持可选字段 `inline_delivery=true`。客户端直连下载失败时，用**同一幂等键、同一请求体**加上这个字段再请求一次，服务端代取已结算的图片后按 base64 返回。该字段**不计入幂等指纹、不产生新计费**；
   - **计费前拒绝错误码**：服务端因并发护栏、限流等原因在**受理计费之前**拒绝时，返回 503 和专用错误码（例如 `IMAGE_RATE_LIMITED`），保证这一类拒绝一定没有扣费，客户端据此才允许同键等待重试；其他 5xx 不得使用这个错误码；
   - 出图请求体按白名单校验，出现未登记字段（模型名、张数、画质等）直接拒绝；
   - 账户服务：余额与消费记录查询（分页）；售后工单提交（只收用户原话文本）和工单状态查询，返回工单编号；
   - 凭证失效统一返回 401，客户端据此自动清除本地凭证；
   - **同设备账户复用接口**（G1 决定启用时才做）：接收客户端提交的凭证单向指纹（最多 5 个），匹配到同一账户时，经用户确认后为本技能签发该账户下的新凭证；只收指纹、不收凭证本身。
3. **扣费时机**：图片生成成功之后、返回之前，与写流水放在同一事务；余额不能为负。
4. **AI 生成标识**：建议在输出图片里写入 AI 生成元数据（XMP 或 C2PA），方便卖家满足平台和法规的披露要求。
5. **安全**：模型 Key 只在服务器环境变量里；不进代码、日志、报告（报告里只写末 4 位）；提交前 `git grep` 检查。
6. **零消耗冒烟测试**：测试账号和测试设备走模拟出图，计费、402、付费页跳转走真实逻辑。
7. **不得影响**：Temu 独立付费页和其他已上线技能的行为不变。
8. **交付报告格式**：改动文件、实际接口（**与约定不一致的逐条列出**）、付费页链接示例、测试结果、环境变量清单。

Codex 用电脑操作第三方网站时，必须写明禁止点击的按钮（运行、订阅、升级、取消），只许查看。

### 阶段 5：客户端技能包

**SKILL.md 总体要求**

- frontmatter 的 description 按第五章 Skill-SEO 规范写，末尾带触发词。
- description、README 和对用户说的话术里，严禁出现开发过程的内容（固定规则第 10 条）；给 AI 的执行指令只写在正文执行说明里。
- 固定话术由 `welcome_copy.py` 输出，SKILL.md 要求 AI 原样转述，不得改写。
- SKILL.md 分两部分：前半部分面向用户（卖点、调用示例、不调用场景、示例说法），后半部分以「执行规范（以下面向宿主助手，不整段向用户复述）」开头。
- 写「触发意识」：用户没说「生图」「做图」，但表达了想要一张画面的意图时（例如「这篇文章缺个封面」），同样使用本技能，不反问「你是要生成图片吗」。
- 每一步按脚本返回的信号和退出码分支处理，并写出对用户说的话。
- 手机端用卡片式列表，不用宽表格（首轮示例的两列链接表除外）。
- 不向用户暴露错误码、字段名、token 等技术词；链接从脚本输出原样复制，不得手打。
- 篇幅控制在 15KB 以内。

**1. 首次使用：付费后置流程（强制）**

核心原则：**先给看得见的价值，再谈钱。用户还没看见你能做出什么，就不该看见付款入口。** 不得跳过价值展示直接谈钱。

整个流程按顺序走：**首轮价值 → 方案与付费确认 → 授权 → 最后一步（充值）→ 开工**。本机已有账户且有次数时，确认后直接开工，跳过授权和充值。

**首轮：价值展示（不提账户、不提套餐、不给付款或授权链接、不报价）**

新用户在本技能的对话里第一次开口时都走首轮，不论用户是只说「你好」、只发了图、发图但没说要改什么，还是已经提出了明确需求。不需要用户先问「有什么功能」或同意看示例。

1. **欢迎句**：固定规则第 1 条，同一对话只说一次。
2. **真实积极反馈**（仅在用户发了参考图时）：用 1–2 句说出图里**实际可见**的优点，例如主体、光线、色彩、构图、氛围。只说看得到的事实，不编造细节、不诊断问题、不先列缺陷、不评价外貌。没有图时不假装看过图。
3. **一个主推方案和预期效果**：读 `references/scenes.md` 路由表命中场景，只给**一个**最适合这张图或这条需求的方向，用一句话说明预期效果。首轮不堆多个方案，不报尺寸、档位、比例等参数，不复述提示词。
4. **示例图表**：运行离线示例命令（例如 `client.py --demo`），按下方「示例预览」交付。
5. **轻确认收尾**：有图或有明确需求时，只说一句「这个方向可以吗？」；没有图、只是问候或问能力时，问「你想从哪个方向开始？」，不强迫用户上传图片。

首轮同时运行落盘命令并带 `--defer-entry`（或等价参数），只在本机保存用户原话和参考图路径；**不取授权链接、不建账户、不调上游、不扣次数**。唯一的网络动作是固定规则第 12 条的首次对话上报，它失败也不影响首轮。不运行 help、account、health、catalog 这类命令，不检查凭证。用户在首轮就问价格时，如实说「按张计费，档位和金额在充值页上，确认方案后我带你过去」，不在对话里报价。

**为什么首轮不能取授权链接**：授权链接通常只有几分钟有效，用户看完示例、确认方案时多半已经失效。

**示例预览（首轮价值展示）**

- 包内放一组**离线示例图**（`assets/demos.json`，8–12 张，覆盖本技能搜索量和使用量最高的场景，个数取偶数；示例资源总大小要控制，以平台上传包大小限制为准，压缩后再放进包里）。示例命令只把包内资源释放到本地，**不联网、不读凭证、不产生费用**；用户说「不要生成新图片」时也可以展示。
- 交付格式：先说一句「都是效果示例图，不是你的真实结果」，再用**两列的 Markdown 表格**（行数 = 示例数 ÷ 2）给出可点击链接。每格写成 `**[标题](命令实际返回的绝对路径)**<br>一句短说明`。链接一律取命令本次实际返回的路径，不手工拼路径，不用 `![](...)` 内嵌图片或 widget；SKILL.md 里的路径占位符只是模板，绝不能原样发给用户。
- 命令只返回了部分示例时，按实际返回的项缩减表格，不补造图片或路径。命令失败时只重跑同一条命令一次，仍失败就如实说「这次暂时没能展示示例图」，不用真实生成来补图，也不因此引导开通或收费。
- **同一对话只展示一次**，以当前对话记录为准；仅加载了 SKILL.md、命令执行成功或本地已有缓存，都不算已经向用户展示过。不检查凭证或安装状态来判断要不要展示。
- 用户说「只要文字」「不要看图」时，只做简短文字说明，不运行示例命令。用户只想看某一个效果时，按对应的示例 key 只展示这一项。用户提到的场景没有对应示例时，如实说明，不拿别的图冒充。
- 示例图必须是本技能真实生成、我们有权使用的图；不含未经授权的真实人物肖像和他人品牌。
- 授权、充值或已确认任务的续接过程中，不插入新一轮首轮介绍和示例。

**方案与付费确认（用户认可方向之后）**

1. **方案与范围确认**：一次问清改哪张图、要做什么、成品用途、必要的边界（只改指定区域，还是允许调整周围画面），并按用途推荐档位（见第 9 节）。事实性变量缺失时一次性合并提问，不循环盘问。效果受限或实验性的场景（例如扩图、多图合成）必须在这里预告。
2. **明确同意付费执行**：用一句话复述最终要点和费用事实，例如：「按 <用途/档位> 做 <内容>，大约需要 <时长>。这一步按张计费，费用以充值页和本次服务记录为准。确认开始吗？」只有用户作出「确认开始」「按这个做」这类**明确肯定的回答**后，才进入凭证检查和实际出图。
3. **以下都不算同意付费执行**：沉默、「无异议」、疑问句、认可示例图、认可首轮推荐、同意授权、授权刚完成、「已充值」（除非之前已经明确确认过同一个任务）。
4. 范围确认和付费确认可以在同一轮说清，但「明确同意」这道闸门不可省略。不写死单价，不承诺赠送次数或折扣。

**授权（本机没有账户时）**

0. **同设备账户复用（G1 决定启用时）**：本技能在本机没有凭证时，先检测本机其他自家技能是否已经绑定账户。检测在本机完成，只把凭证算出的**不可逆单向指纹**（加固定域分隔串，最多 5 个候选）交给服务端匹配，**不传凭证本身**。匹配成功后，**先征求用户确认**（例如「检测到你在本机其他技能里已经开通过账户，要直接用这个账户吗？确认后这里不用再授权」），用户同意才签发本技能的凭证；用户拒绝后本地记住，不再检测；提供关闭开关（环境变量）。SKILL.md 必须写明这一机制、提交了什么、怎么关闭。匹配失败、用户拒绝或检测出错时，走下面的正常授权。
1. 用户已经明确同意付费执行、但本机没有账户、且没有走通同设备账户复用时，**这时才取授权链接**。
2. 授权话术**原样转述**，依次包含：
   - 你确认的方案已经存好了；
   - 首次出图需要先完成一次授权，**授权本身不扣费**；
   - 「现在需要你做的」编号清单，写明不用手机号、不用验证码、不用 API Key；
   - 授权链接（Markdown 链接语法）；
   - 链接几分钟有效，过期可以重取，方案不受影响；
   - **到这一步为止没有产生任何扣费**；
   - 跨技能提示（第 4 节）。
3. **授权是「出图路上的一道关卡」，不是「请先注册」**，措辞以脚本输出为准，不得改写成注册口径。
4. **续接优先**：用户说已授权、但本机没检出账户时，先重跑一次查询命令接续领取，只有命令明确报会话过期或作废时，才引导重新授权。不得一上来就让用户从头再走。
5. 链接过期就重新取一次，用短版话术，不重复整段引导，但两句定心话（第 3 节）照样保留。
6. 页面没有弹出来时，如实告诉用户可以手动点链接，或者说一声重新取一个。不得声称页面已经打开而实际没开。

**最后一步：充值（账户已关联、余额为零）**

1. 用户说「已授权」后，运行查询命令，确认账户真的关联上了。
2. 余额为零时，原样转述「最后一步」话术，依次包含：
   - 账户已关联；
   - **「只剩最后一步：选个套餐补充余额」**，选完立刻按用户确认的方案出图；
   - 档位和金额在页面上，**不在对话里报价**；
   - 付款后即时到账，方案不用重说；
   - 充值链接。
3. **要把这一步说成「最后一步」**。用户已经走了好几步，每一步都被告知没扣费，到这里他想知道的是「还差多远」。
4. 宿主有内置浏览器或预览工具时，用它打开充值页；没有就把链接给用户自己点。不得用脚本强行调起系统浏览器、绕开宿主设置。

**开工（到账后续接）**

- 只有之前已经明确同意过**同一个任务**的范围、用途/档位和费用条件，才按已确认的方案继续。开工前用一句话复述要点（画什么、横版还是竖版、几张、是否本地排中文标题），**内容缺一不可**；这是告知，不再重新征求同意。
- 之前只认可了方向、只同意了授权，还没有明确同意付费执行的，先补上付费确认，等用户明确同意后再开工。授权完成或充值完成，都不能推定为同意任意生成或任意费用。

**用户表示暂不开通时**（任何一步都适用）：只回一句固定话术「没问题。等你需要图片的时候随时叫我。」然后结束。不再推销、不追问原因、不重发链接，也不索要任何凭证。用户已经确认的方案保留，下次回来直接继续。

**2. 话术骨架：责任交接闭环（强制）**

从用户确认方案到付款，每一步的话术都按同一个结构写。固定话术由 `welcome_copy.py` 输出，AI 自己补充话术时也按这个结构：

```
我这边做完了什么（已经把 X 准备好了 / 已经确认过 Y）
         ↓
### 现在需要你做的：编号清单，一步一个动作
         ↓   ← 清单里必须有兜底：页面打不开、链接过期了怎么办
做完跟我说一声，我接着做什么（点名用户确认的那个方案）
         ↓
两句定心话
```

- **「我这边做完了什么」**：让用户感到「已经推进到这一步，现在轮到你」，而不是「被拦住、请先注册」。
- **兜底只能写真实存在的路径**。写之前先读服务端代码确认；服务端没开放的方式（例如在对话里填手机号验证）不得写进去。

**3. 两句定心话（强制，从授权这一步起每一步都要重复）**

1. **「你确认的方案已经存好了，不用重新描述。」**
2. **「到这一步为止，没有产生任何扣费。」**

这不是啰嗦。用户是在「还没花钱」的状态下一步步往前走的，这两句就是他肯往前走的理由。少说一次，他就可能停在授权页前面。

**4. 跨技能提示（强制，口径要准）**

账户的通用额度在多个技能间共享时，首次引导开通必须主动说：「已经在其他技能开通过账户？同一账户的通用次数在已接入的技能间共享，这里不用重新付费。」

口径不能说过头：
- 通用次数共享；
- 次数是否永久有效，以充值页的既定口径为准；
- 旧版专用余额单列，仍在原产品里使用；
- Temu 企业套餐和它的免费体验是独立口径，不归入通用套餐，也不拿来类比；
- 通用通道**不设免费体验**。

**5. 到账与余额口径（全包统一）**

- 收款侧有实时监控和一键发放时，可以说「**即时到账**」。但**到账以服务端返回的真实次数为准**：用户说「我付了」不等于已经到账，仍要运行付款核对命令。「已登记」和「已到账」必须分开显示。**不能把用户自述当作已到账。**
- 用户说「已付款」后的标准回复：「已收到你的付款登记。到账是即时的，稍等一下说一声『继续』我再查一次。图片需求已保留，到账就接着做。」
- **全包口径必须一致**，包括话术、脚本输出和所有 references。一处说「即时」、另一处说「等核款」，用户会按慢的那句来预期。改这类口径要全包搜索一遍。
- **每次付费交付后报账**：原样转述服务端返回的「本次 {charged}，剩余 {balance}」，数值直接取自脚本输出，**禁止自行计算**。
- **余额偏低提醒**：服务端返回低余额标记时（阈值由后台配置），追加一句「余额不多了，回复『充值』我为你打开充值页。」用户同意后才取充值链接；不列档位、不报金额。
- **任务进行中余额不足**：如实说明还没开始生成、这次没有产生生成费用、任务已保留；然后**先问用户是否打开充值页**，用户明确同意后才取链接。交付链接时说明「页面打开不等于已经下单，充不充、充多少都由你决定」。用户拒绝或暂不决定时保留任务，不催促。

**6. 引导边界、账户服务与转介**

- **完整的能力介绍只在两种情况出现**：新用户首次使用、用户主动问能做什么。用户问能力时统一回到首轮结构（欢迎句已说过就不再说）。授权和充值流程中途不插入任何引导话术或能力清单。
- 引导中不承诺赠送次数，不提具体价格，不提内部技术。
- **账户意图优先**：用户问账户、余额、次数、充值、订单时，按账户意图处理，不当成生图需求，也不重新跑首轮。识别自然说法，不要求用户逐字输入固定口令。
- **余额与消费记录**：用户说「查余额」「消费记录」时，首行显示余额，最近几条记录用两行卡片展示（时间 · 内容 · 金额 · 状态），末尾提示「共 N 条，回复『查看所有』可看全部」。
- **反馈与售后**：用户想表扬、提建议、反馈问题或对费用有疑问时，先听完，把原话整理确认后提交工单，告诉用户反馈编号和处理时限（以后台承诺为准），用户之后说「查工单」即可查看结果。服务暂时不可用时先记下内容，稍后再提交。费用相关的回答只引用服务端返回的计费记录。
- **链接一律用 Markdown 链接语法**给出，不贴裸链接（手机端的长裸链接不能点）。链接从脚本输出原样复制，每次请求都取新链接，不复用对话里的旧链接。
- **相邻需求正向转介到自家技能**：用户要的是本技能不做、但我们另一个已上架技能能做的事，直接推荐过去（例如「这个需求用 <自家技能名> 更合适，把图发到那边就行」）。转介目标只能是已上架的自家技能。
- **不承接、也没有自家技能可转介的需求如实告知**，不变通承诺：纯后期处理（调曝光、裁剪、去噪）；视频和动图；只要文案不要图。不得用「换背景」「重新做一下」之类的说法变通承诺本技能做不到的效果。

**7. 对客边界：不讲实现**

- 对用户只说用途、效果、实际限制、费用事实和下一步。用户追问时，也只解释能感知到的用途、效果和限制，不披露内部信息，不编造自研能力或厂商承诺。
- **不点名模板、不复述提示词、基线段或参数适配**。模板选择和提示词拼装只在执行时用。交付时只说这次实际改了什么、尽量保留了什么、有哪些可见的限制，例如「去掉了路人，尽量保持人物原貌和构图」。
- 不讲服务提供方、模型名称、接口、处理机制。
- **对客禁用词**统一维护一份清单（例如「上游」「管线」「pipeline」「模板」「基线」「服务端」「base64」「接口」以及轮询间隔这类机制描述），用测试扫描 SKILL.md 面向用户的部分、README、references 中会被转述的文案，以及脚本里所有对客的进度和提示文案（第 11 节）。

**8. 等待管理**

- 开工前告知等待时长，按有没有参考图、选的档位分别预估，以实测为准。
- **外层超时不低于「请求预算 + 轮询窗口 + 进程余量」**，SKILL.md 命令表和 `references/scenes.md` 两处都写明，数值从脚本常量实算。**所有出现超时数值的地方必须一致**：SKILL.md 正文、命令表、参数表、内部约束、references、脚本注释，由测试逐处比对，脚本常量一改，文案全部跟着改。请求超时调大时，外层超时同步重算（请求预算 + 轮询窗口 + 计费前拒绝的等待上限 + 进程余量）。超时设得太低，会在任务已提交、次数已占用之后把进程砍掉，用户看到报错，钱却已经花了。
- 提交后由脚本自己轮询（间隔和轮数写成脚本常量），进度信息走 stderr 播报，播报文案不提轮询机制。轮询用完还没结果时保留原任务后退出；用户说「继续」，就沿原任务查询，**不新建任务、不换幂等键**。
- 等待期间**不催促、不重复发起、不换参数重发**，因为重复提交可能重复计费。这句要写进话术。
- **轮询不得吞掉异常后报「仍在处理」**。分别记录轮询次数和成功拿到应答的次数：拿到过应答、仍在处理 →「仍在处理」；一次都没连上 →「当前进度未能确认」；明确失败 → 按失败处理。
- **费用结论只说服务端能确认的**：服务端明确返回未扣费时，可以说「这次没出图，没有扣次数」；拿不到明确结论时（例如完全没有应答），只说「费用以服务记录为准」，不猜测已扣或未扣。

**9. 出图与交付**

- **档位按用途讲，不讲参数**：清晰度或尺寸档位一律翻译成用途，例如「人像推荐档，优先保留原貌」「高清通用档，适合风景和商品」「打印级」。路由表每个场景写好推荐档位（见第 10 节）；涉及人物的场景默认用保真档，换成更高档位前如实说明「人物细节可能有变化」，只有用户明确要打印或正式用途时才建议最高档。
- **成功时先把图交给用户**，再简述这次实际改了什么、尽量保留了什么、有哪些可见限制（第 7 节，不点名模板），然后按第 5 节报账。
- **交付时告诉用户原图没有改动**：用户发来的原图不修改、不移动，结果一律另存为新文件。
- **首次交付成功后附一次完整的调整引导**，此后不再重复，例如：「想调整直接说，比如『标题区再留大一点』『背景换成浅木色』；换个用途也直接说就行。」之后每次交付最多附一句建议，而且只在明显可优化时给。
- **后续调整不暗示免费**：调整需要重新生成时，先说明可能再次按张计费，取得明确同意后再执行。
- **失败话术按四拍写**：结果 → 原因 → 费用 → 零成本的下一步。原因属于我方服务端时，一律说「服务正在处理较多请求」，不说「不稳定」「出了点问题」「服务异常」，不承诺恢复时间；网络原因如实说网络连不上。费用按第 8 节的口径说。例如：「这次没有拿到图——服务正在处理较多请求。这次没有扣次数。稍后想再试，直接告诉我『重新生成』。」只有用户主动要求技术排查时，才提供脱敏后的错误码。
- **尺寸偏差如实告知**：实际尺寸和请求尺寸不一致时（例如请求 1080×1440，实际 1024×1536），只说实际结果，并提出可以本地裁切。不得把请求尺寸当成成品尺寸报给用户。
- 输出目录生成 `index.html` 画廊，方便一次查看全部图片。
- **大图下载**：服务端返回直连下载地址时，脚本分段下载、弱网自动续传。
- **直连下载失败自动内联补取**：云端沙箱常按域名白名单拦截图片域名，直连下载会必然失败。下载失败时，脚本用同一幂等键、同一请求体加 `inline_delivery=true` 请求一次，由服务端代取后按 base64 返回，**不产生新计费，每单最多一次**；进度只说「正在换一种方式取回图片」。补取也失败才说「图片下载暂时未完成，费用以服务记录为准，请不要重复生成」。
- 参考图格式报错时，点名是哪个文件、什么问题；本地校验不通过时不联网。参考图保持原图分辨率传递，尽量保留细节。
- **支持的参考图格式以服务端实际支持为准**（固定规则第 11 条）；未经确认的格式在 SKILL.md 标注「待服务端确认后再放开」，不得先对用户承诺。
- 用户要修改时，引导「每次只改一件事」：一句话里提了多个修改，就拆成多次生成依次完成。这句写进 SKILL.md、`scenes.md` 和 `prompts.md`。

**10. 提示词体系（仅供执行，不对客复述）**

- `references/prompts.md`：每个场景一个模板，按「**动作动词 + 具体视觉参照 + 锁定句**」三段式写。空泛形容词（「好看一点」「有质感」）一律换成可核对的视觉描述。
- `references/scenes.md`：路由表，每行三列：**用户口语关键词 → 场景 → 推荐参数**（档位、比例，及升档或降档的条件，例如「打印装裱时升最高档；画面含人物时用保真档」）。
- 选择模板时不得临时自由发挥；未命中路由表时不硬套模板，按三段式公式现场合成。
- **事实性变量**（商品名、活动主题、日期、价格、尺寸、品牌规范）缺失时，一次性合并列出向用户提问，不逐条盘问；用户不提供时按模板示例方向补默认并告知。**审美类变量**（色调、光线、构图、材质）一律自动补稳妥默认，不追问。
- 每条提示词都必须带上三条基线：
  1. **真实性基线**（永远放第一段）：严格还原参考图里的产品，锁定外观、形状、比例、颜色、材质、部件、标签和印字、数量，不增删、不重新设计；
  2. **文字基线**：**底图一律不带文字**，提示词写明「图中不得出现任何文字」；需要标题或卖点文字的图位，由脚本在本地排版叠加。原因：模型生成的汉字常是乱码，本地排字盖不掉，只能重做再扣一次费；
  3. **安全基线**：不出现他人品牌和标志、真人肖像（除非用户提供并授权）、夸大或虚假宣传。
- 有参考图且画面含人物时，另加**人物身份基线**；**多个人物时逐人指代、逐人锁定**（例如「左侧戴眼镜的人」「右二穿蓝衣服的女孩」），不用「所有人」这类笼统说法。向用户预告时说「会尽力保持五官与身份特征，细节差异可能存在」，不承诺像素级一致。
- 效果受限或实验性的场景在模板里标注，并要求在确认环节预告（第 1 节）。

**11. 脚本要求**

- 仅用 Python 3.7+ 标准库。
- **退出码**：0 完成；2 可续接，即等待用户动作（无账户 `onboardingPreview`、余额不足 `needsCredits`、仍在处理 `jobPending`）；3 参数或服务错误（本地参数校验不通过时不联网）；4 凭证已失效并已自动清除（`credentialsReset`）。
- **示例命令**（`--demo [key]`）：只释放包内示例图，输出实际路径数组；不联网、不读凭证、不与出图参数混用；资源缺失时退出码 3。
- **stdout**：一行 JSON 信号，供宿主 AI 判断下一步，后面跟 `welcome_copy.py` 输出的固定话术。宿主按退出码和信号分派，不靠解析中文文案判断状态。话术放在脚本里，是为了逐字稳定、能被测试锁住。
- **`welcome_copy.py` 按步骤分函数**：首轮开场（不含任何链接、账户、价格字样）、授权、授权重取短版、最后一步、开工复述，授权起的每个函数都按责任交接闭环写，带两句定心话。
- **stderr**：只放对客进度信息，文案纳入禁用词测试（第 7 节），不得把异常详情拼进对客文案。
- **请求体白名单**：出图请求只允许约定字段（例如提示词、尺寸、档位、参考图），禁止 AI 或脚本加入模型名、张数、画质等未登记参数。
- **禁止自动重试和定时重试**，只有两个例外：
  1. 已提交任务用原幂等键原地轮询；
  2. **计费前拒绝的同键等待重试**：只有服务端返回专用的「计费前拒绝」错误码（例如 503 + `IMAGE_RATE_LIMITED`）时，才等待后用**原幂等键、原请求体**重试。参考值：每次等 40 秒，每张最多 3 次，整批共用 240 秒等待上限，全部写成脚本常量；上限用完按失败话术收场，不换键、不重新生成。等待时的进度只说「服务正在处理较多请求，稍后自动继续这一张」。其他 5xx、超时、网络错误一律不自动重试。
- 新幂等键只在用户明确要求「重新生成」，或用户明确说「继续」恢复之前因余额不足而结束的同一任务时产生，不因失败或余额不足自动生成第二张。
- 每张图使用固定的请求编号作为幂等键；中断后用同一个编号查询，不重复扣费。
- **凭证失效自愈**：收到凭证失效（401）时，脚本自动清除本地失效凭证，输出 `credentialsReset` 并以退出码 4 结束；宿主直接重新发起原任务即可走授权。**禁止 AI 自己「修理」凭证**：不改凭证文件权限、不打开凭证文件、不安装依赖、不设置环境变量。
- 本地状态放 `~/.<技能>/`，凭据文件权限 600，拒绝符号链接；模型不得读取。断点只存参考图路径、不存字节，恢复时重新读取并校验。
- 输出文件不覆盖已有文件；原图不修改、不移动。
- **契约测试** `tests/test_skill_contract.py` 随包分发：锁住欢迎句和固定话术逐字不变、退出码、信号字段、外层超时值、请求体白名单、示例集合与 SKILL.md 一致、对客禁用词等。

**12. 技能收藏（记忆锚定，强制）**

用户不 @ 技能时，宿主 AI 遇到它自认为能答的问题（例如「见家长带什么」）往往直接回答，跳过技能，只靠 description 很难稳定触发。做法分两步：

| 步骤 | 作用 | 负责 |
|---|---|---|
| 写好 description（第五章） | 让宿主第一次就有机会选中技能 | 拉新 |
| 记忆锚定 | 用户用过一次、点了同意后，引导宿主把「这类问题优先调用本技能」写进宿主自己的长期记忆；之后新对话遇到同类问题会自动调用 | 留存 |

不改宿主底层、不需要后端，只在 SKILL.md 里写规则，由宿主 AI 调用自己的记忆工具完成。实测（送礼顾问技能，2026-10，WorkBuddy）：未锚定时新对话问「下周见女朋友父母带什么好」不调用技能；锚定后显示「加载技能」，按技能流程执行。

**何时询问**

- **只在出图交付成功之后询问**，放在首次交付的调整引导之后。首轮价值展示、付费确认、授权、充值进行中一律不问，失败的那一轮也不问。
- 先检查宿主记忆里是否已有「<技能中文名>收藏」记录。没有记录时，用提问组件问一次（header：收藏技能，单选）：
  问题：要收藏<技能中文名>吗？收藏后，以后问<领域>问题不用 @ 我，也会自动由我来接待。
  - 收藏（description：写入 WorkBuddy 记忆，可随时删除）
  - 暂不
- 已有记录，或用户本次选了「暂不」，本次对话不再询问。**每个对话最多问一次。**
- 用户任何时候说「收藏<技能中文名>」，直接执行收藏。

**收藏时写入的内容**

用宿主自带的记忆工具，同时写入两层：用户级记忆（跨项目的全局偏好）；项目级记忆（当前工作区；没有项目级记忆时只写用户级）。写入内容原样如下，**不添加任何用户个人信息和对话内容**：

```
【技能偏好：<技能中文名>收藏】
凡是<触发场景1>、<触发场景2>、<触发场景3>等问题，优先调用技能 <技能name>（<技能中文名>），按该技能流程执行后再给建议。
```

- 写入成功后回复：「已收藏，以后问<领域>问题会优先由<技能中文名>接待。想取消时说『取消收藏<技能中文名>』即可。」
- 宿主没有记忆写入工具，或写入失败时，如实告诉用户当前环境不支持收藏，**不得假装成功**。
- **取消收藏**：用户说「取消收藏<技能中文名>」时，删除两层记忆里的这条记录，并确认已删除。

**必须遵守**

1. **必须用户同意才写**，禁止静默写入记忆，否则审核会判为越权。
2. 写入内容只有「调用偏好」一句话，**不写会过期或不真实的承诺**，例如「已开通，无需再授权」「继续不重复扣费」「默认用某档位」「免费」。
3. 必须提供取消方式。
4. 记忆里的技能 name 必须和 SKILL.md 的 name 完全一致；技能改名后旧锚定失效，要重新收藏（固定规则第 7 条）。
5. SKILL.md 的合规部分加一行：「技能收藏只在用户点击『收藏』或明确要求后写入宿主记忆，写入内容仅为技能调用偏好，不含任何用户个人信息，用户可随时取消。」

**局限**：只对用过一次并点了收藏的用户生效，首次触发仍靠 description；最终调不调用由宿主模型决定，锚定能明显提高命中率，但不是百分之百；不同宿主、不同版本的记忆机制可能不同，上线前按阶段 6 实测。

### 阶段 6：测试

写一个**按接口约定实现的模拟后端**和**端到端检查脚本**，每次改动后重跑，连同契约测试全部通过才能进入阶段 7。必测场景：

**账号与计费**

- [ ] 未关联账号 → 提示关联 → 浏览器确认后继续
- [ ] 正常出图并扣费，余额正确
- [ ] 多图套装中途余额不足 → 402 → 充值后用同一编号继续，已出的图不重复扣费
- [ ] 内容策略拒绝不扣费
- [ ] 上游 5xx 不扣费，用同一编号重试成功
- [ ] 同一编号重放不重复扣费
- [ ] token 失效自动清除并提示重新关联

**引导与确认**

- [ ] 首轮脚本输出不含 `http`、套餐、充值、付费、开通账户、价格字样；欢迎句逐字一致
- [ ] 首轮调用零 HTTP（把请求函数换成抛异常的函数实测；首次对话上报除外，且失败不影响本轮）
- [ ] 示例命令不联网、不读凭证；返回的示例 key 集合与 SKILL.md 示例表、README 的个数和标题完全一致；资源缺失时退出码 3
- [ ] SKILL.md 含「不得跳过价值展示直接谈钱」「两列」示例表「都是效果示例图，不是你的真实结果」「这个方向可以吗？」，不含「三个方案」
- [ ] SKILL.md 列明「不算同意付费执行」的情形：沉默、无异议、认可示例、认可推荐、同意授权、授权完成
- [ ] 授权话术含「授权本身不扣费」
- [ ] 授权起，每一步话术都含「方案已经存好了」和「没有产生任何扣费」
- [ ] 授权和最后一步话术都含「### 现在需要你做的」编号清单，兜底项含「打不开」
- [ ] 话术里不出现服务端未开放的授权路径
- [ ] 本机已有账户且有次数 → 跳过授权和充值，直接制作
- [ ] 用户拒绝开通 → 只回固定一句后结束，不重发链接，方案保留
- [ ] 全包没有旧的慢到账口径；SKILL.md 含「不能将用户自述当作已到账」和「以服务端真实次数为准」
- [ ] 声明的外层超时 ≥ 请求预算 + 轮询窗口 + 计费前拒绝等待上限（从脚本常量实算，不写死）；全包所有超时数值一致（测试逐处比对 SKILL.md、references、脚本注释）
- [ ] 开工复述齐全，内容不缺项；未明确同意付费执行的，授权或充值后先补确认再开工
- [ ] 任务中途余额不足 → 先问是否打开充值页，同意后才取链接；话术含「页面打开不等于已经下单」
- [ ] 账户类说法走账户菜单，不触发第一轮
- [ ] 首次对话上报只含白名单字段，每个安装只发一次，关闭开关生效；开口统计按第六章第 5 节验收
- [ ] 首次对话上报不挂在可能走不到的分支上：首轮示例命令、无凭证预览退出这些提前返回的分支，退出前都已经发出过上报（测试逐个分支断言）

**等待轮询（六种时序）**

- [ ] 一次就出图
- [ ] 两轮后出图
- [ ] 五轮都还在处理
- [ ] 首轮网络抖动后恢复
- [ ] 全程连不上 → 说「当前进度未能确认」
- [ ] 明确失败 → 不扣费

**交付**

- [ ] 成功时先交图；首次交付附一次调整引导，之后不重复
- [ ] 失败话术按四拍；我方服务端原因只说「服务正在处理较多请求」；拿不到明确费用结论时说「费用以服务记录为准」
- [ ] 每次付费交付后转述服务端返回的本次扣费和剩余，余额低时追加充值提醒
- [ ] 交付话术说明原图没有改动；后续调整需要重新生成时先说明可能再次计费
- [ ] 大图分段下载，断网后续传成功
- [ ] 直连下载失败 → 同键同体加 `inline_delivery` 补取成功，不产生新计费；补取失败才走失败话术
- [ ] 计费前拒绝错误码 → 按常量等待并同键重试，单张次数和整批等待上限生效；其他 5xx 不重试
- [ ] 同设备账户复用（启用时）：只提交指纹；用户确认前不签发；拒绝后不再检测；关闭开关生效；失败时回到正常授权
- [ ] 请求体出现未登记字段时被拒绝（客户端和服务端各测一次）
- [ ] 凭证失效 → 自动清除、退出码 4，重发原任务走授权
- [ ] **对客禁用词测试**：SKILL.md 面向用户部分、README、references 转述文案、脚本所有对客进度文案中不含禁用词清单里的词（进度文案用 AST 从脚本里取出所有字符串常量来扫）
- [ ] 查余额与消费记录、提交工单、查工单各走通一次
- [ ] 实际尺寸与请求不一致时提示并提出裁切
- [ ] 输出目录有 `index.html` 画廊
- [ ] 参考图格式报错点名具体文件
- [ ] 离线检查不调用后端
- [ ] 输出文件不覆盖

**技能收藏（记忆锚定）**

- [ ] @ 技能完整走一次，交付后弹出收藏卡片；付费或购买流程中途不弹
- [ ] 点「收藏」后，宿主记忆管理里用户级和项目级各有一条记录，内容只有调用偏好一句话
- [ ] 选「暂不」后，本次对话不再询问
- [ ] 开新对话，不 @ 技能，直接问一句该领域的问题 → 出现「加载技能 <技能name>」，并按技能流程执行
- [ ] 说「取消收藏<技能中文名>」→ 两层记忆里的记录都被删除
- [ ] 宿主不支持写记忆时，如实告知不支持，不假装成功

Temu 版本额外测：新用户免费 1 次只生效一次，文案保留。

**真机行为验收（`tests/first-turn-preview.md`）**

脚本单元测试通过，不能证明宿主 AI 会按顺序执行。另写一份真机验收单，在真实宿主（如 WorkBuddy）里逐条验收：

- 验收前核对宿主实际加载的是新版 SKILL.md（市场安装的副本路径通常带 `__skillhub` 后缀）；**每次改完都开新对话测**，不用已经加载旧版的对话。
- 全程只用包内离线示例和测试账号，不做真实付费出图。
- 按可见的工具调用和最终回复判定，不要求看模型内部推理。
- 必测场景（每条写清输入和可观察的通过标准）：只发图、只说「你好」、问能力、带图提明确需求、已有账户的新对话、「不要生成新图片」、「只要文字」、同一对话已展示过示例后再提需求、只看某一项示例、认可方向（不得当成付费同意）、明确同意付费、只同意了授权就完成授权（须补确认）、已确认任务完成授权后续接、任务中途余额不足、「已充值 / 继续」、拒绝开通。
- 列出判失败的情形：没有真实积极反馈或编造细节、首轮堆多个方案或参数、示例不是两列链接表或用了内嵌图片、把模板占位符原样发出、把认可或沉默当成付费同意、未经同意打开充值页、暗示后续调整免费、失败时猜测费用。
- **真机没跑完只能标「待验收」，不得写成已通过**；G4 提交真机验收结果。

模拟后端和检查脚本交给 Codex，用来验证服务端与客户端兼容。

**上架前零消耗验证**：负责人用浏览器打开 `/pricing` 确认返回正确；核对模型或接口 Key 的末 4 位。

### 阶段 7：上架准备（⛔ G4）

- 上架包：`mps-<技能>-<版本>.zip`，直接上传，不用解压。
- 上架文案按第五章写，过一遍自查清单。
- 专家包和技能包同时发布时，两边文案、计费、欢迎句一致。
- 保留上一版上架包，用于回滚。

### 阶段 8：上线监控与迭代

宿主（如 WorkBuddy）版本更新后，重跑一次真机行为验收和技能收藏的测试步骤，确认首轮顺序和记忆锚定仍然生效。

上线后头几天每天看：

1. **出图失败率和策略拒绝率**；
2. **首轮转化**：首次对话 → 认可方向 → 同意付费执行 → 完成授权 → 付费，哪一步掉得最多先改哪一步；
3. **售后工单**：数量、类型、处理时效，每周看一次；
4. **重新生成率**（高说明还原度或提示词有问题）；
5. **付费转化和客单价**；
6. **单张成本与收入**。

每两周按第五章第六节复盘一次上架文案。

**版本号**：功能大改升主版本，修提示词、改话术升修订号。

**回滚**：技能包重新上传上一版；后端按版本目录切回上一版（数据库迁移要可回退）。回滚前告知负责人。

## 四、踩坑记录

| 问题 | 结论 |
|---|---|
| 首次开口上报挂在走不到的分支上，漏斗第一步一直是 0 | 第一轮由脚本主动发，提前返回的分支返回前都要已发出；上线第一天确认数据进来 |
| 标识写不进去时临时造一个，同一台机器被算成很多新设备 | 写不进就跳过这次上报，不临时造标识 |
| 只看单日报表，以为转化很低 | 跨日充值会被单日报表漏掉，看 7 天以上窗口 |
| 凭记忆或只按 SOP 摘要开发 WorkBuddy 包，字段或目录与官方要求不符，提交后解析失败 | 每次开工先读 WorkBuddy 官方开发文档线上最新版，冲突时以官方为准 |
| 用户不 @ 技能时，宿主自认为能答就直接回答，技能没被调用 | description 写用户原话加调用倾向句；用户用过一次后，经同意做技能收藏（记忆锚定） |
| 静默把调用偏好写进宿主记忆 | 必须用户点「收藏」才写，否则审核判为越权 |
| 把和 AI 的开发对话、修改原因写进了上架简介和 description | 原则性错误。面向用户的文字只写用户需要知道的，上架前逐句检查 |
| 指令只发在对话里，Codex 找不到 | 合并成一份完整规格文件，放进工作目录 |
| 幂等缓存了 402，充值后重试一直余额不足 | 只缓存成功响应 |
| 用户换了新对话被当成新用户 | 用方案 A，网站记住浏览器登录态 |
| 欢迎句被改写 | 欢迎句固定，只换技能名 |
| 出图前没确认费用，用户有异议 | 出图前必须确认张数，并说明「按张计费，以实际账单为准」 |
| 产品印字被模型改错 | 提示词第一段真实性基线，并列出产品上的全部印字 |
| 底图里让模型直接写中文，生成乱码汉字，本地排字盖不掉 | 底图一律不带文字，文字由脚本本地排版；否则只能重做再扣一次 |
| 轮询吞掉异常，连不上也说「仍在处理」 | 分别记录轮询次数和应答次数，一次都没连上就说「当前进度未能确认」 |
| 外层超时太短，图还在生成就被判失败，用户重提又扣一次 | 外层超时不低于 420 秒，脚本输出写明重复提交会再扣费 |
| 首轮 20 秒内把付款入口送到用户眼前，结果 211 个下载 0 个付费订单 | 付费后置：首轮先给真实反馈、一个主推方案和离线示例图，确认后才授权，最后才谈钱 |
| 云端沙箱拦截图片域名，已扣费的图下不来 | 直连失败后同键同体加 `inline_delivery` 由服务端代取补发，不重新计费 |
| 服务端并发满时直接判失败，用户只好重新生成 | 计费前拒绝用专用错误码，客户端同键等待重试，有次数和总时长上限 |
| 调大了请求超时，SKILL.md 有的地方还是旧数值 | 所有超时数值由测试从脚本常量逐处比对 |
| 堆触发词时删掉了和自家技能的分界句，互相抢触发 | 触发说法写全，分界句保留 |
| 首轮只有几段文字方案，用户看不见效果 | 首轮展示离线示例图（两列链接表），不联网、不收费 |
| 首轮就取授权链接，用户确认方案时链接已过期 | 用户明确同意付费执行后再取链接 |
| 把「无异议」、认可示例或授权完成当成同意付费 | 只认明确肯定的回答；不算同意的情形逐条写进 SKILL.md 并测试 |
| 对用户点名模板、复述提示词和机制 | 对客只讲改了什么、保留了什么、有什么限制；禁用词用测试扫描 |
| 失败时说「服务不稳定」「出了点问题」，或猜测已扣费 | 四拍话术；我方原因统一说「服务正在处理较多请求」；费用以服务记录为准 |
| 余额不足时直接打开充值页 | 先问，同意后才取链接，并说明打开不等于下单 |
| AI 自己改凭证文件权限、装依赖去「修」凭证 | 凭证失效由脚本自动清除，禁止 AI 自行修理 |
| 只跑了单元测试就当成验收通过 | 另做真机行为验收，开新对话测，没跑完标「待验收」 |
| 说「请先注册」，用户觉得前面都是铺垫，停在授权页 | 授权说成「出图路上一道一次性的关卡，不扣费」，授权起每一步重复两句定心话 |
| 兜底写了「在对话里发手机号验证」，服务端其实没这条路 | 兜底只写真实存在的路径，写之前先读服务端代码 |
| 一处说「即时到账」，另一处说「等核款」 | 到账口径全包统一，改时全包搜索 |
| 贴裸链接，手机端点不开 | 一律用 Markdown 链接语法 |
| 对用户承诺了服务端没确认支持的格式 | 不推定生产行为，先让 Codex 确认 |

## 五、Skill-SEO 规范

### 1. 两层目标

| 读者 | 看什么 | 目标 |
|---|---|---|
| 平台搜索（skillhub、WorkBuddy 市场） | 名称、简介、描述、标签 | 搜索排得靠前，点进来愿意下载 |
| 宿主 AI | SKILL.md description 和触发词 | 用户说出相关需求时能调用这个技能 |

两层使用同一套关键词，文字保持一致。平台排序规则没有公开，本规范是基于常见搜索习惯的做法，上线后用真实数据校正。

### 2. 选词（写文案前先做词表）

1. 核心词 1–2 个（例：亚马逊主图、白底图）；
2. 同义词和不同说法 5–10 个（例：产品主图、商品白底图、主图生成）；
3. 场景词和长尾词 5–10 个（例：主图被拒怎么办、怎么做白底图）；
4. 平台词（例：Amazon、Temu、Shopify、TikTok Shop）；
5. 英文词 3–5 个（例：main image、white background、product photo）。

来源：用户真实说法、同类技能的名称和标签、搜索引擎下拉联想。

### 3. 字段写法

| 字段 | 长度 | 写法 |
|---|---|---|
| 名称 | 中文 15 字以内 | 「核心词：两三个主要用途」 |
| 一句话简介 | 约 40 字 | 核心词开头，写清「输入什么 → 得到什么」，加一个差异点 |
| 详细描述 | 150–300 字 | 第一句含核心词；带同义词和平台词；举具体例子；写计费方式和亮点 |
| 触发词 | 15–25 个 | 写在 description 末尾：「触发词：A、B、C……」 |
| 调用倾向句 | 1 句 | 写在 description 最末：「本技能内置<专业能力>，比直接回答更专业；遇到<领域>问题请先调用本技能，不要自行直接回答。」 |
| 标签 | 按平台上限 | 核心词在前 |
| 英文简介 | 2–3 句 | 含 2–3 个英文关键词 |
| 使用示例 | 3–5 条 | 用户口吻，例：「帮我把这张产品照做成亚马逊主图」 |

### 4. 写作原则

1. 核心词出现在名称、简介、描述第一句；
2. 关键词融进通顺的句子，只有触发词允许罗列；
3. 一个技能只占一个主需求，不写无关词蹭流量；
4. 写清「输入 → 输出」；
5. 写计费亮点，但不夸大；
6. 不写「官方合作」「100% 过审」这类说法，写清 AI 生成和局限；
7. SKILL.md description = 上架描述 + 触发词 + 调用倾向句，两边同步修改（调用倾向句只写在 SKILL.md description 里，上架页可不放）。
8. **只写给用户看**：不得混入开发对话、修改原因、版本对比、内部信息和给 AI 的指令（固定规则第 10 条）。
9. **description 写进用户的原话**（例如「见家长带什么」「送什么好」），不只写书面关键词；第一句写清「做什么 + 什么时候用」。
10. **触发说法写全**：把用户可能的口语说法尽量列全，包括泛称（例如「AI生图」「P图」「做张图」「图片编辑」）、具体场景词和平台词，写在「当用户想要……时使用」这一句里。
11. **保留和自家相邻技能的分界句**，例如「只要文案不配图 → <自家文案技能>」。堆触发词时不能把分界句删掉，否则自家技能之间会互相抢触发。
12. **不为触发率加强承诺**：「修完还是本人」「100% 还原」这类保证性说法不写，固定规则第 8 条优先。

### 5. 自查清单

- [ ] 名称含核心词，15 字以内
- [ ] 一句话简介以核心词开头，写清「输入 → 输出」
- [ ] 描述第一句含核心词，至少 3 个同义词，有具体例子，写了计费方式
- [ ] 触发词 15 个以上，覆盖核心词、同义词、场景词、英文词
- [ ] 标签按优先级排
- [ ] 3–5 条使用示例
- [ ] SKILL.md description 与上架描述一致
- [ ] 无夸大、无官方合作或认证说法，写了 AI 生成和局限
- [ ] 欢迎句符合固定格式
- [ ] description 含用户原话；末尾有且只有一句调用倾向句
- [ ] SKILL.md 有「技能收藏」章节，合规部分有收藏说明一行
- [ ] 逐句检查过所有面向用户的文字：没有开发对话、修改原因、版本对比、内部信息或给 AI 的指令

### 6. 上线后优化

每两周复盘一次：

- 收集用户实际说法，补进词表和触发词；
- 看漏斗：曝光低 → 关键词不对；详情页访问多、下载少 → 简介没讲清价值；下载多、首次使用少 → 触发词不够或首次门槛高；
- 每次只改一个字段，看一周再改下一处，记录修改日期。

## 六、开口统计与转化漏斗（强制，新技能必须严格执行）

**为什么要做**：用户第一次在对话里用技能（首次开口）完全发生在用户本机，以前后台看不见，「下载 → 首次开口 → 激活 → 付费」里最前面的一段是盲区。首次对话上报把这一步变成可统计的指标。**新技能不接这套统计，不得上架。**老技能升级时一并补上。

### 1. 客户端上报规范

1. **两个标识**，都是本机随机生成的**规范小写 UUIDv4**：
   - `installation_id`：每个技能、每次安装一份，存在技能目录里；
   - `machine_id`：每台机器一份，存在我们自己的目录（例如 `~/.mps/machine-id`），只在我们自家技能之间共用；不读取硬件信息，不是设备指纹。
2. **标识文件的处理**：文件不存在、内容损坏（不是规范 UUIDv4、或有乱码）时，原地重新生成并写回；**写不进去就跳过这次上报**。绝不在进程里临时造一个标识凑数，否则同一台机器会被算成无数个新设备，把漏斗数据搞乱。
3. **上报内容**：固定规则第 12 条的字段，`skill_id` 为 kebab-case、不超过 64 个字符。字段名、大小写、格式和服务端白名单完全一致，多一个字段整条会被拒。
4. **只发一次**：每个安装成功发出后，在本地写一个标记，之后不再发。服务端按 IP 每天有上限，同样的内容重发不会被合并，每次都占额度。
5. **发送时机**：第一轮由脚本主动发出，**不能挂在可能走不到的分支上**。首轮示例命令、无凭证预览退出这些会提前返回的分支，返回前都要已经发过。
6. **不打扰主流程**：有界超时（2–3 秒）、不重试、失败静默放弃，不影响业务输出和退出码。上报域名固定在白名单里，环境变量改不了。
7. **接到账户上**：账户关联时，把 `installation_id`、`machine_id`，以及装机渠道、运行环境（只按操作系统区分电脑本机、手机本机、云端沙箱）一起带给服务端。服务端不认这些可选字段时，去掉后用同一个幂等键重发一次，保证关联本身不受影响。
8. **开关与披露**：按固定规则第 12 条提供关闭开关，在 SKILL.md 里披露；开发和测试时 `is_test=true`。

### 2. 服务端规范（写进阶段 4 给 Codex 的规格）

1. **上报接口**：匿名，不要凭证，成功返回 204；请求体严格白名单（多字段即拒）；每个 IP 每天上限 50 次（数值后台可配）；校验两个标识必须是规范小写 UUIDv4。
2. **事件表**：至少包含 `id`、`skill_id`、`installation_id`、`machine_id`、`ip_day_hash`、`occurred_at`。`ip_day_hash` 是 IP 按日加盐的哈希，**不存明文 IP**；明细保留 180 天。
3. **安装或关联表**加 `installation_id`、`machine_id` 两列，用来把首次开口和账户串起来。
4. **上线顺序**：服务端数据库迁移和接口先上线、在测试环境验证通过，再发布带上报的客户端。迁移没装的环境，漏斗按 0 计，不报错。
5. **管理台**：漏斗接口和每一步的明细下钻接口（L0 明细一行一台新设备，不返回 `ip_day_hash`）；另附一个和管理台同口径的离线报表脚本，两边数字必须一致。

### 3. 转化漏斗口径（只统计新用户）

漏斗只看新用户。老账户装新技能不算进漏斗，用下面第 4 节的独立指标看。

| 步骤 | 口径 | 数据来源 |
|---|---|---|
| L0 首次开口（新设备） | 窗口内首次出现的 `machine_id`：该机器历史上第一条首次对话上报落在窗口内 | 首次对话上报事件表 |
| L1 打开授权页（新访客） | 授权页的页面访问事件中，`ip_day_hash` 历史首现落在窗口内；PV 只数匿名访问，UV 按哈希去重 | 页面访问事件表 |
| L2 完成授权（新账户） | 窗口内新建、且首次关联的账户（方案 A 的页面确认完成） | 账户表、设备关联表 |
| L3 打开充值页（新账户） | 充值页到达事件，经设备凭证对应到账户；只算账户创建时间落在窗口内的；按账户去重 | 充值页访问事件 |
| L4 首充成功（新账户） | 窗口内新建账户的第一笔入账：支付订单入账和未挂订单的账本充值逐条去重，按账户取最早一笔 | 订单表、资金流水表 |

我们的流程没有「在对话里提交手机号」这一步（方案 A），所以漏斗比原口径少一步；如果以后加了别的验证步骤，按同样方法插入一级。

**时间窗口**：按北京时间自然日。查询某一天 D，从 UTC 的 D-1 日 16:00 起，到 UTC 的 D 日 16:00 止；按天数查询时用 UTC 滚动窗口。

**注意跨日低估**：账户 D 日创建、D+1 日才充值，单日报表里不会算进首充，所以**单日报表会系统性低估转化**。判断转化率看 7 天以上的窗口。

### 4. 三个独立指标（和漏斗分开看）

| 指标 | 管理台名称 | 口径 |
|---|---|---|
| 技能启用数 | 技能启用数 | 窗口内 `installation_id` 历史首现的个数，按技能分组；按这台机器是不是窗口内的新设备，拆成「新设备」和「老设备」。老设备装新技能的首次开口，漏斗 L0 不算，这里算 |
| 技能激活数 | 技能激活数 | 窗口内新增的技能与账户绑定数，拆成「新账户」和「老账户」 |
| 充值笔数 | 充值笔数 | 窗口内全部入账笔数（支付订单入账、账本充值），按支付渠道拆分 |

渠道看板用「技能启用数」除以对应渠道的下载数，算出「下载 → 开口」比值。

### 5. 上线与验收

- **G1**：确认本技能的漏斗步骤怎么对应（上面的表要按本技能实际流程填写），哪些步骤数据不可得。
- **阶段 6**：
  - 用测试账号（`is_test=true`）从首次开口走到首充，管理台每一步都能看到这条测试数据，明细下钻能查到；
  - 标识文件损坏、目录只读、断网时，主流程不受影响，并且不会产生临时标识；
  - 同一安装重复运行只上报一次；
  - 管理台和离线报表脚本的数字一致。
- **G4**：提交上面的验收结果。
- **上线第一天**：确认正式数据开始进入；如果是 0，先查服务端迁移是否已装、客户端是否真的发出，不要等。
- **阶段 8**：每天看 L0 到最后一步的漏斗和三个独立指标；哪一步流失最大，先改哪一步。
